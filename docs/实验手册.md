| 结论 | 对应实验 | 最少数据 | 论文材料 |
|------|----------|----------|----------|
| 硬件与传感器链路正常 | 实验一 | `/odom`、`/imu`、`/livox/lidar` 频率截图 | 硬件平台与话题表 |
| FAST-LIO 能生成可导航地图 | 实验二 | 1 张最终 `my_lab.pgm/yaml` + 1 张 RViz 点云截图 | 建图结果图 |

| 里程计约束创新有效 | 实验四/五 | 3 组同 bag 基线/改进轨迹 | 消融实验主结果 |
| 退化检测不是"常开约束" | 实验四/五 | `[OdomStat]` 触发率 20%-60% 左右 | 创新机制有效性 |
| 正常场景不被改进算法拖坏 | 实验四/五 | 3 组普通房间/开阔区同 bag 对照 | 非退化场景反证 |
| 退化感知优于简单常开融合 | 实验四/五 | `baseline / improved / always-on` 三组轨迹 | 机制消融表 |
| SLAM 精度改善可量化 | 实验五 | 平面闭环漂移、几何误差、RPE 汇总 | 定量表格 + 误差棒 |
| 改进定位能提升端到端导航 | 实验六 (T2 必经长走廊) | 同目标点基础定位 vs 改进定位 | 成功率/耗时/路径效率/平滑性表 |
| 导航性能满足任务需求 | 实验六 | 至少 3 类场景、每类 3 次 trial | 成功率/耗时/路径效率/速度平滑性表 |
| 退化触发集中在退化区域 | §7.9 (N1) | 改进版 + 常开版的 `degradation_spatial_*.png` | 空间分布图, 红点聚集走廊段 |
| 阈值不是"凑出来的" | §7.10 (N2) | feat × res 3×3 网格的触发率/漂移表 | 敏感性表, 论文一张关键表 |
| 静止启动守卫有效 | §7.11 (R2) | 启动时遥控 vs 静止 1s 的同地点 bag 对比 | §7.5 守卫验证, 1 段对比文字 |
| 创新无显著实时性开销 | §9.5 (R3) | baseline vs 改进 CPU/RAM/帧延迟 | 附录实时性对比表 |

> **不建议写 APE 作为主指标**：本项目没有动捕/RTK 等绝对真值。使用 baseline 当参考计算的 APE
> 不是绝对精度，答辩时容易被追问 ground truth 来源。应以平面闭环漂移、已知几何距离误差、
> RPE 和导航成功率作为主要实验指标。

> **闭环漂移的 anchor 校核 (R1, 零成本)**: 录每段 bag 时, 用胶带在地面标出**起点圆点 + 朝向箭头**,
> 回到起点时尽量按胶带停车并拍照. 评估闭环漂移时若胶带物理重合, 报数据采用脚本计算值;
> 若停车明显偏离 (>15 cm), 在 `experiment_log` 元数据中记录补偿量并在论文里说明.
> 这样能把"人工停车误差"从主指标中剔除, 否则单次几十 cm 的停车污染会让漂移指标失去说服力.

```bash

# 验证安装

python3 -c "import pandas; print(pandas.__version__)"   # 应 >= 2.x
```

> **注意 1 — evo 安装失败 (ARM64 架构)**: 可尝试 `pip3 install evo --no-build-isolation`。
>
> **注意 2 — `numpy.dtype size changed` 错误**: 根因是 apt 装的 `python3-pandas 1.3.5`
> (按 numpy 1.x ABI 编译) 遇到 pip 装的 numpy 2.x 时二进制不兼容。修复:
> ```bash
> pip3 install --user "pandas>=2.2"   # 用户空间装 pandas 2.x, 不动系统包
> ```
> 这会在 `~/.local/.../site-packages/` 装一份新 pandas, 屏蔽 apt 的旧版.
>
> **注意 3 — `cannot import name 'docstring' from 'matplotlib'` 错误**: 这是 apt 的
> `python3-matplotlib 3.5.1` 与 pip 的 matplotlib 3.10+ 在 `mpl_toolkits` 命名空间

> 这个冲突只影响 `evo_traj` 子命令的 seaborn 链路; `evo_rpe` 不受影响.
> [evaluate_slam.sh](../scripts/evaluate_slam.sh) 阶段 3 的轨迹对比图**已改为直接调用
> matplotlib**, 不走 `evo_traj`, 避开此冲突. 因此实际只需 `evo_rpe` 能跑即可,
> 不必死磕 `evo_traj`.

## 3. 常见编译错误排查

### 3.1 FAST-LIO 编译错误

**错误**: `fatal error: nav_msgs/msg/odometry.hpp: No such file or directory`
```
原因: nav_msgs 头文件未找到
解决: sudo apt-get install -y ros-humble-nav-msgs
```

**错误**: `Eigen 相关的模板实例化错误`（密密麻麻的模板报错）
```
原因: 里程计约束代码中的矩阵维度可能不匹配
解决: 检查 apply_odom_position_constraint() 中：
      - H 矩阵维度应为 2x23（仅约束 X/Y，不约束 Z；不是 2x24，因为 DOF=23）

      - dx 维度应为 23x1
```

### 4.4 验证遥控器控制

驱动节点启动后，机器人会站起来但遥控器**暂时无法**控制机器人行走。
这是因为驱动节点以 500Hz 持续发送 `STAND_UP` 指令，覆盖了遥控器的输入。

**激活遥控器**（必须执行）：在另一个终端手动发送一条零速度指令：
```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist '{}'
```
该指令将驱动模式从 `STAND_UP(6)` 切换到 `WALK_W_VEL(2)`，之后遥控器即可正常控制。

**验证遥控器已生效**：
```bash
# 用遥控器控制机器人行走，同时观察 /odom 数据变化
ros2 topic echo /odom --field pose.pose.position
# 推动遥控器摇杆，x/y 值应该变化
```

> **注意**: 每次重新启动 `unitree_driver_launch.py` 后都需要重新执行上述激活命令。
> 建图和导航的 launch 文件中包含了 `unitree_driver`，同样需要这一步。

### 4.5 LiDAR → body 外参测量（**实机部署必做**）

> **目标**: 测量 MID-360S 相对 Go1 机体的安装位置，并写入 launch 文件。  
> **重要性**: 外参是 SLAM 精度的基础，误差 >2cm 会直接反映到点云错位和地图扭曲。

#### 4.5.1 坐标系约定

遵循 ROS REP-103：
- `body` 帧 = FAST-LIO 输出并供 Nav2 使用的本体帧；工程上按机器狗腰部几何中心
  （四腿投影中心点，水平面的机体中线交点）近似测量外参
- `livox_frame` 帧原点 = **MID-360S 外壳底部**（Livox 手册标注的传感器坐标系原点，不是外壳几何中心）
- 两帧的坐标轴方向一致：**X 前、Y 左、Z 上**

> ⚠️ 常见误区：Livox MID-360 系列的 frame 原点是**雷达外壳底面**，不是外壳几何中心。若按外壳中心测量会系统性偏高约 3 cm。

#### 4.5.2 测量步骤

让机器狗站立在水平地面、**头朝前**。

**Z 偏移（垂直方向，最关键）**：
- 直接可测方案：用卡尺/直尺测 "LiDAR 外壳**底面** ↔ 机体腰部中心" 的垂直距离即为 `z`
- 腰部中心不可直接触及时，可通过 `(背部顶面到地 + 腹部底面到地) / 2` 估算腰部中心高度 `h_body`，再用 `z = h_lidar_bottom - h_body`
- Go1 站姿下 `h_body` 约 0.28–0.32 m

**X 偏移（前后方向）**：
1. 找到机身前后中线（左右两前髋 / 左右两后髋中点连线交汇处）
2. 从机身中心垂直于地面画一条参考线，测 LiDAR 底部中心到这条线的水平距离
3. LiDAR 在机身**前方** → `x` 为**正**；在后方 → 负

**Y 偏移（左右方向）**：
1. 找机身左右中线（两前腿或两后腿投影中点连线）
2. 测 LiDAR 底部中心到中线的水平距离
3. LiDAR 偏向**左侧** → `y` 为**正**；偏向右 → 负

**姿态（roll / pitch / yaw）**：
- 绝大多数夹具是水平固定 → 三个角都 = `0.0`
- 若 LiDAR 朝下倾斜（抬地面感知）：用量角器测倾角 `α°`（度），`pitch = -α × π / 180`（弧度，向下倾为负）
- 若 LiDAR 偏向一侧安装（Y 轴转角）：测 yaw 角，单位弧度

#### 4.5.3 当前实测值（2026-04-17）

```
y =  0.000   m   (居中，无左右偏移)
z =  0.2742  m   (LiDAR 外壳底部比腰部中心高 274.2 mm)
```

## 5. 实验二：SLAM 建图（FAST-LIO 在线建图 + PCD 离线切片）

> **目标**: 生成 Nav2 可用的 2D 占据栅格地图，供后续导航使用  
> **前提**: 实验一硬件验证通过

### 5.0 路线选择说明（为什么不用 slam_toolbox）

项目原先采用 `slam_toolbox`（2D 扫描匹配 + Karto 图优化）实时生成栅格地图。
实验中发现：Go1 的高频 Z 轴颠簸 + Pitch 俯仰抖动会让 `pointcloud_to_laserscan`
输出的 2D 扫描畸变；在长廊等几何退化场景下，slam_toolbox 扫描匹配的旋转约束
很弱，**走 8 字型路径二次经过同一位置时会出现明显角度偏差**（重影 / 错位）。

而 FAST-LIO 同时融合 IMU + LiDAR，ikd-Tree 增量子地图的 3D 点云质量明显更高，
**肉眼检查即能确认 3D 地图无明显漂移**。

因此项目采用 **路线 B**：
1. 在线阶段：只跑 FAST-LIO，启用 `pcd_save_en` 累积全局 3D 点云；
2. 离线阶段：用 `pcd_to_map.py` 把 PCD 在 Go1 腰部以下高度带切片，栅格化为
   Nav2 标准 `pgm + yaml`；
3. Nav2 栈（map_server / AMCL / Planner / Controller）**一字不改**照常加载。

### 5.1 启动在线建图

```bash
# 建图时不融合足端里程计（避免 EKF 引入的额外噪声影响 PCD 一致性）
ros2 launch go1_bringup go1_mapping.launch.py use_odom_fusion:=false
```

这会启动：`unitree_ros` + `livox_driver`（MID-360S）+ `FAST-LIO2` +
`pointcloud_to_laserscan`（仅用于 RViz 可视化，不喂给 slam_toolbox 了）。
**不再启动 slam_toolbox**。

> **注意**: 如果机器狗未开机，`unitree_driver` 节点会报错退出（`CONNECTION IS NOT AVAILABLE`），
> 但这**不影响**建图功能。LiDAR → FAST-LIO 的数据链路完全独立于机器狗驱动。
>
> FAST-LIO2 启动后的前 2-3 秒会输出 `No point, skip this scan!` 警告，这是 IMU 初始化的正常现象。

**关键配置确认** — `FAST_LIO/config/mid360.yaml` 中：
```yaml
pcd_save:
    pcd_save_en: true    # 必须 true
    interval: -1          # -1 = 全部帧累积到一个 PCD 文件
```

FAST-LIO 在进程收到 `SIGINT`（Ctrl+C）时把累积的全局点云保存到
`~/go1_ws/src/FAST_LIO/PCD/scans.pcd`。

**rosbag 自动录制**（`go1_base.launch.py` 默认行为）：
- 每次启动都会在 `~/go1_ws/bags/mapping/<YYYY-MM-DD_HH-MM-SS>/` 下生成一份 bag，
  录制 `/livox/lidar`、`/livox/imu`、`/odom`、`/imu`、`/tf_static`、`/cmd_vel`、`/Odometry`
- 消融实验回放 (§7) 会直接使用这些 bag；无需额外命令
- 关闭录制：`ros2 launch go1_bringup go1_mapping.launch.py record_bag:=false`
- 自定义目录：`... bag_dir:=/path/to/output`
- `go1_replay.launch.py` 本身不启动 rosbag 录制；若你用 `go1_base.launch.py
  use_sim_time:=true` 做其他离线调试，必须额外加 `record_bag:=false`，
  否则会把回放数据再写一遍到新 bag，容易误用

**建图归档自动化**（`go1_mapping.launch.py` 默认 `auto_archive:=true`）：
- Ctrl+C 退出后，launch 自动调用 `ros2 run go1_bringup archive_map`，把
  `~/go1_ws/src/FAST_LIO/PCD/scans.pcd` 复制到 `~/go1_ws/src/go1_bringup/maps/sessions/<时间戳>[_label]/`，
  同时一次性生成 4 套过滤变体（`raw / sor_only / cc_only / both`）+ `compare.png` 对比图
- **防覆盖**：FAST-LIO 每次启动都会覆盖 `scans.pcd`，归档目录里的副本是该会话的
  唯一原始记录（已加入 `.gitignore`，不入仓但本地永久保留）
- 加标签：`ros2 launch go1_bringup go1_mapping.launch.py archive_label:=lab_run1`
- 关闭自动归档：`... auto_archive:=false`，之后手动跑：
  `ros2 run go1_bringup archive_map --label lab_run1`
- **耗时**：750 MB PCD ≈ 1.5 分钟（SOR 占 60% 时间），Ctrl+C 后终端会停留这段时间

### 5.6 离线切片生成 2D 地图

> 默认情况下 §5.1 的 `auto_archive` 已经一次性生成了 4 套变体地图，
> 直接进 `maps/sessions/<时间戳>/` 选用即可（推荐用 `both.{pgm,yaml}`）。
> 本节是手动单次切片的命令，调试 / 重切片时使用：

```bash
ros2 run go1_bringup pcd_to_map \
    ~/go1_ws/src/FAST_LIO/PCD/scans.pcd \
    ~/go1_ws/src/go1_bringup/maps \
    my_lab \
    --z-min 0.05 --z-max 0.25 \
    --resolution 0.05 \
    --hit-threshold 2 \
    --padding 0.5 \
    --sor-k 20 --sor-std 2.0 \
    --min-blob-size 5
```

依赖：`numpy` + `scipy`（Jetson 上 `sudo apt install python3-scipy` 一次）。

参数说明（位于 FAST-LIO 的 `camera_init` 帧；该帧 **Z=0 在启动时机器人 body/IMU 位置**，约离地 0.30 m，**不是地面**）：

| 参数 | 含义 | 调优建议 |
|------|------|----------|
| `--z-min / --z-max` | 切片高度带（米，camera_init 系） | 默认 `[0.05, 0.25]` ≈ 离地 0.35–0.55 m，落在 LiDAR 安装高度（≈0.57 m）下方，能稳定捕获走廊/房间连续墙面。**想包括低矮障碍（椅腿、箱子）需下探到负值**（如 `[-0.20, 0.05]`，对应离地 0.10–0.35 m）；若地面凹凸大导致地面被当墙，反向抬高 `z-min` |
| `--resolution` | 栅格分辨率（米/格） | 默认 0.05，与 Nav2 costmap 默认一致 |
| `--hit-threshold` | 单格需累计多少次命中才算占据 | 默认 2，降噪；若稀疏场景漏墙调到 1；稠密噪点多调到 5 |
| `--padding` | bbox 外扩（米） | 防止地图紧贴点云边界；Nav2 做路径规划时机器人需要至少 inflation_radius 的自由空间 |
| `--sor-k` | 3D SOR 近邻数 | 默认 20（PCL 推荐），设 0 关闭离群点去除 |
| `--sor-std` | 3D SOR σ 倍数 | 默认 2.0；越小过滤越激进（1.0 会连墙面边缘都剔掉，谨慎） |
| `--min-blob-size` | 2D 占据斑块最小像素数 | 默认 5（8-邻接），小于此阈值的孤立占据块退回空闲；设 0 关闭 |

**杂点过滤两级策略**：

1. **3D 统计离群点去除（SOR）**：栅格化**之前**，对每个点查 k 近邻的平均距离，
   剔除距离 > 全局 `μ + std·σ` 的点。等价 PCL `StatisticalOutlierRemoval`。
   主要清除玻璃反射 / 动态物残影 / IMU 积分噪声造成的"飞点"——这些点经常
   单独漂在真实墙面外 5~20 米处，不过滤的话会严重拉大 bbox 让地图变空旷。
2. **2D 连通域过滤**：栅格化**之后**，对占据格做八连通标记，小于 `min_blob_size`
   个像素的孤立块整块退回空闲。去除切片平面上的 1~4 格毛刺，墙面（几十上百格）
   不会被误伤。

输出：
- `my_lab.pgm` — P5 灰度图（0=占据, 254=空闲, 205=未知）
- `my_lab.yaml` — Nav2 `map_server` 标准元数据

脚本会输出每一步的统计，典型值：
```
[1/5] 加载 PCD: .../scans.pcd (523.1 MB)
        读取 16,345,945 个点, Z 范围 [-0.950, 5.979]
[2/5] 3D SOR 离群点去除 (k=20, std=2.0)
        剔除 355,254 点 (2.17%), 剩余 15,990,691
[3/5] Z 切片 [0.05, 0.25] + 栅格化 (res=0.05 m)
[4/5] 连通域过滤 (min_blob=5): 占据 631 -> 573 (剔 58 毛刺格)
        最终尺寸 210x359, 占据 573 格, 空闲 74,817 格
        origin (世界坐标, 左下角): (-6.600, -2.866)
[5/5] 写入 PGM: .../my_lab.pgm
```

**关闭过滤对比**（加 `--sor-k 0 --min-blob-size 0`）：同一份点云未过滤时栅格被
飞点撑到 414×875，过滤后收紧为 210×359，可直观看到 SOR 剔除了远距离离群点。

### 5.7 归档目录与晋升地图

每次建图（默认 `auto_archive:=true`）会产生一个会话目录：

```
~/go1_ws/src/go1_bringup/maps/sessions/2026-04-21_17-10-54_lab_run1/
├── scans.pcd          # 原始点云副本 (~750 MB, .gitignore 已排除)
├── raw.pgm/yaml       # 无过滤 baseline
├── sor_only.pgm/yaml  # 仅 3D SOR
├── cc_only.pgm/yaml   # 仅 2D 连通域过滤
├── both.pgm/yaml      # 双级 (推荐使用)
├── compare.png        # 4 宫格对比图 (论文素材)
└── summary.txt        # 各变体的 SOR/CC 剔除统计
```

挑一次满意的会话，把 `both.*` 同步为 Nav2 默认加载的 `maps/my_lab.*`：

> ⚠️ **`--promote` 行为限制**：[archive_map.py](../go1_bringup/archive_map.py) 的 `--promote`
> 是"**用当前 `FAST_LIO/PCD/scans.pcd` 重新跑一次完整切片，然后把新生成的 `both.*` 复制
> 为 `my_lab.*`**"。它**不能**回头晋升历史会话目录里已有的 `both.*` —— 因为 `scans.pcd`
> 是会被下一次建图覆盖的单一文件。
>
> 实际工程语义:
> - "刚建完图, 还没跑下一轮" → `--promote` 等价于"用本次会话的 PCD 切片产出 my_lab"。
> - "之前建了 N 次, 想晋升第 N-1 次的归档" → `--promote` 不能用 (它会读最新的
>   `scans.pcd` 而不是历史会话目录里的副本)。这种情况要走方法 2。

```bash
# 方法 1 (仅当 scans.pcd 是你想要的那次): 用 archive_map.py --promote
#         它会重新跑 4 变体并把新生成的 both.* 同步到 maps/my_lab.*
ros2 run go1_bringup archive_map --promote

# 方法 2 (推荐, 任何时候都能用): 直接 cp 已归档会话的 both.*
#        sessions/<时间戳>/scans.pcd 是本次会话的 PCD 副本, 不会被后续建图覆盖
cd ~/go1_ws/src/go1_bringup/maps
SESSION_DIR=sessions/2026-04-21_17-10-54_lab_run1   # 改成你想晋升的目录
cp "$SESSION_DIR/both.pgm" my_lab.pgm
# yaml 里 image: 字段需手动改成 my_lab.pgm
sed 's|image: both.pgm|image: my_lab.pgm|' \
    "$SESSION_DIR/both.yaml" > my_lab.yaml
```

**论文图片**：直接拷贝 `compare.png` 到论文目录，4 宫格已自带变体名称、参数、
栅格尺寸、占据/空闲数标注，可直接作为 figure。

**人工肉眼检查**：墙体应为连续黑线、走廊应为连续空闲区（白色）、8 字路径的
两次经过**不应有重影**（如果 FAST-LIO 3D 本身无漂移，2D 图也不会漂移）。

> **如果地图质量差（墙断裂 / 噪点多）**：
> - 切片高度带不合适 → 调整 `--z-min/--z-max`（注意 camera_init 系 Z=0 在 body 启动位置，不是地面）
> - 空旷区飞点、bbox 被撑很大 → 降 `--sor-std`（如 1.5）或提高 `--sor-k`（如 30）
> - 墙外孤立斑点 / 小毛刺 → 提高 `--min-blob-size`（如 10）
> - 整体噪点多 → 提高 `--hit-threshold`
> - 本质是 FAST-LIO 3D 就有问题 → 回到 §5.2 先把 `/cloud_registered` 看清楚，

### 6.3 低风险导航链路检查（首次上机必做）

> **目标**: 在真正发送导航目标之前，确认 Nav2 生命周期、TF、传感器、代价地图和速度链路都正确，
> 将风险控制在"机器人尚未运动"阶段。

**安全准备**：
- 场地中央留出至少 `2m x 2m` 空地，机器人前方 1m 内不要站人。
- 遥控器保持在手边，确认能随时切回手动/急停。
- 第一次只使用 `use_odom_fusion:=false` 基础模式；确认基础导航稳定后再测试在线改进模式。

**阶段 A — 不发目标，只验链路**：

```bash
# 1) Nav2 生命周期节点应全部 active
for n in map_server amcl planner_server controller_server behavior_server \
         bt_navigator waypoint_follower smoother_server velocity_smoother; do
  echo "=== $n ==="
  ros2 lifecycle get /$n
done

# 2) FAST-LIO 与 pointcloud_to_laserscan 数据频率（观察 5-10 秒后 Ctrl+C）
ros2 topic hz /Odometry
ros2 topic hz /scan

# 3) TF 链路: FAST-LIO 启动后 camera_init -> body 必须存在
ros2 run tf2_ros tf2_echo camera_init body

# 4) 速度链路: Humble 下应为 controller -> cmd_vel_nav -> smoother -> /cmd_vel -> unitree
ros2 topic info /cmd_vel_nav -v
ros2 topic info /cmd_vel -v
ros2 param get /velocity_smoother max_velocity
ros2 param get /velocity_smoother max_accel

# 5) 代价地图应能发布。若卡住, 通常是 camera_init -> body TF 不存在
ros2 topic echo /local_costmap/costmap --once
```

**通过判据**：
- lifecycle 查询均为 `active`。
- `/Odometry` 和 `/scan` 都有稳定频率（通常约 10Hz）。
- `tf2_echo camera_init body` 能连续输出位姿。
- `/cmd_vel_nav` 的订阅者包含 `velocity_smoother`；`/cmd_vel` 的发布者应是 `velocity_smoother`。
- `velocity_smoother max_velocity` 应为 `[0.3, 0.2, 0.7]`，没有把 `vy` 压成 0。
- 不发送目标时 `/cmd_vel` 不应持续输出非零速度。

**阶段 B — 初始化定位后再验 map 链路**：

**阶段 C — 第一次低速短距离目标**：

## 7. 实验四：SLAM 消融实验（足端里程计融合验证）

> **目标**: 通过 rosbag 离线回放，在完全相同的传感器输入下，对比加入/不加入足端里程计融合对 SLAM 精度的影响  
> **前提**: 实验一硬件验证通过

### 7.1 消融实验方法论

**为什么用 rosbag 离线回放？**

| 方案 | 优势 | 劣势 |
|------|------|------|
| 在线两次实跑 | 简单 | 无法保证路线完全一致，不公平 |
| **rosbag 离线回放** | 完全相同的输入数据，严格可复现 | 需要 `use_sim_time` 配置 |
| 导航层消融 | 验证端到端效果 | 变量太多，不适合单一因子消融 |

**主实验变量**: `odom_constraint.enable`（开/关）。同一个 rosbag 分别回放基线与改进版，
其余输入数据、外参、下采样、尾部盲区过滤等参数完全相同。

**机制消融变量**: `odom_constraint.force_degraded`。在 `odom_constraint.enable:=true`
的基础上设置 `force_degraded:=true`，所有成功约束帧都按退化高权重处理，得到
`always-on` 常开强约束对照组。它用于证明本文方法不是"简单把里程计全程强塞进 FAST-LIO"。

**场景要求**:

| 场景 | 目的 | 采集要求 |
|------|------|----------|
| 退化闭环路线 | 证明长廊等几何退化段漂移降低 | 走廊段 ≥30m，闭环回到起点，重复 3 次 |
| 非退化普通路线 | 证明正常场景不劣化 | 开阔教室/大厅/普通房间闭环，避开长直走廊，重复 3 次 |

### 7.2 数据采集（在真机上）

设计两类闭环路线，分别服务于"退化改善"和"正常不劣化"两个论文结论。

建议每次上机前先创建一个实验会话目录，现场记录、轨迹、日志和结果都放在同一处：

```bash
ros2 run go1_bringup experiment_log init \
    --kind slam_degradation \
    --label degradation_exp1 \
    --location "实验楼三层走廊" \
    --route "教室A-长走廊-教室B-返回教室A"
```

命令会打印会话目录，例如 `~/go1_ws/experiments/2026-05-01_14-30-00_slam_degradation_degradation_exp1/`，
其中 `metadata.yaml` 用于现场勾选状态，`geometry_constraints.csv` 是几何约束模板，
`COMMANDS.md` 会生成本次实验的录包、三组回放和评估命令。

**A. 退化闭环路线**（主实验）：
```
[起点/终点: 教室A] -> [走廊(退化段, 30m+)] -> [教室B] -> [走廊返回] -> [教室A]
```

**B. 非退化普通路线**（反证实验）：
```
[起点/终点: 教室/大厅] -> [开阔区绕行] -> [桌椅/墙边转弯] -> [回到起点]
```

非退化路线应尽量避开长直走廊，目标是让 `force_degraded:=false` 的改进版触发率很低，
同时闭环漂移、几何误差不明显差于基线。

**步骤一: 测量已知几何距离**

在采集数据**之前**，用卷尺测量实验场地中的几个关键距离，记录到 CSV 文件中。
这些数据将作为 SLAM 精度的"已知几何约束"参考:

```bash
# 创建约束文件 (示例，请根据实际场地修改)
cat > ~/go1_ws/trajectories/geometry_constraints.csv << 'EOF'
# 标签, 实测距离(m), 起点x, 起点y, 终点x, 终点y
# 注意: 起点/终点坐标是 SLAM 轨迹中的大致坐标, 首次先空着,
#       跑完第一次 SLAM 用 evo_traj 俯视图读取后再填入
走廊长度,30.5,0.0,0.0,0.0,0.0
房间A对角线,8.2,0.0,0.0,0.0,0.0
房间B宽度,6.0,0.0,0.0,0.0,0.0
EOF
```

> **提示**: 起点/终点的坐标需要跑完第一次 SLAM 后, 用 `evo_traj --plot_mode xy`
> 画俯视图, 读出对应位置的大致 (x, y) 坐标后回填。首次运行评估脚本时
> 如果没有此文件会自动跳过, 不影响平面闭环漂移的计算。
>
> ⚠️ **重要**: ROS REP-103 坐标系下俯视图是 XY 平面 (X 前、Y 左, Z 上)。
> **必须用 `--plot_mode xy`**, 不要用 `xz`. 用 `xz` 画出来的是侧视图,
> 读到的第二个坐标是 Z (高度, 近似恒定), 把它当 Y 填进 CSV 会让"房间宽度"
> 类侧向约束完全失效. 若已按 xz 填过数据, **必须重采集**。

**步骤二: 录制传感器数据**

`go1_base.launch.py` 现在**默认自动录制 rosbag**（见 §5.1），只需启动并走完即可：

```bash
# 终端 1: 启动底层驱动 + FAST-LIO2 + 自动 rosbag 录制
ros2 launch go1_bringup go1_base.launch.py \
    use_odom_fusion:=false \
    bag_dir:=$HOME/go1_ws/bags/degradation_exp1

# 用遥控器控制机器人沿预定路线行走
# 走完闭环后 Ctrl+C 停止录制, bag 保存在 bag_dir/<时间戳>/
```

退化路线**重复 3 次**，每次传入不同 `bag_dir`：
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp1`
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp2`
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp3`

非退化路线也**重复 3 次**：
- `bag_dir:=$HOME/go1_ws/bags/normal_exp1`
- `bag_dir:=$HOME/go1_ws/bags/normal_exp2`
- `bag_dir:=$HOME/go1_ws/bags/normal_exp3`

> **关键提醒**:
> - 起点和终点必须尽量重合（计算平面闭环漂移的前提）
> - 退化路线的走廊段至少 30m，以确保几何退化发生
> - 非退化路线不要刻意走长直走廊，用来证明改进算法在正常场景不造成明显副作用
> - 行走速度保持 0.2-0.3 m/s，与正常工况一致
> - 自动录制会包含 `/Odometry` 便于在线核对轨迹；离线消融回放时只播放
>   `/livox/lidar /livox/imu /odom /imu`，避免算法输出话题与重跑结果冲突。

**1. 退化事件 WARN (每个退化瞬间都会打印, 节流 2 秒)**:
```
[WARN] Geometric degradation detected! feat_num=132, res_mean=0.172. Applying odom constraint with high weight.
```
这说明走廊段被正确识别为退化区域，足端里程计约束被激活。

**2. 统计汇报 INFO (每 100 帧一次, 由 evaluate_slam.sh 自动提取)**:
```
[INFO] [OdomStat] degraded=157/500 (31.4%), feat_num=412, res_mean=0.082
```
这条日志里的百分比就是**退化触发率** — 评估创新是否真正生效的关键指标。

> ⚠️ **关键验证 — 触发率必须 > 0 且在合理区间**
>
> 若 `evaluate_slam.sh` 阶段 5 显示触发率 < 20%:
> - 说明**退化判据偏严**, "改进版"大部分时段仍用 `odom_noise_normal=10` 运行,
>   与基线的漂移差距主要来自"常开弱约束", 论文立论说服力不足。
> - **排查路径**: 降低 `degradation_feat_threshold` (如 200→100) 或抬高
>   `degradation_residual_threshold` 的容忍度 (如 0.15→0.10 反向调整, 即更容易判退化),
>   重新跑 §7.4 和 §7.5 评估。
>
> 若触发率 > 60%:
> - 说明阈值**过于宽松**, 改进版接近全程强约束, 失去"仅退化时增强"的语义, 退化与正常场景无差异。
> - **排查路径**: 提高 `degradation_feat_threshold` 或降低 `degradation_residual_threshold` 重跑。
>
> **合理区间**: 20%-60% — 走廊段触发、室内开阔段不触发, 符合"选择性增强"的设计意图,
> 与 [evaluate_slam.sh](../scripts/evaluate_slam.sh) 阶段 5 的判据、
> [algorithm_design.md](algorithm_design.md) 的论文口径保持一致。
> 可跨 3 次实验查看方差，若波动过大需检查场地一致性。

> **提示**: 截图保存 `[WARN] Geometric degradation` 和 `[OdomStat]` 日志，作为论文中退化检测有效性的佐证。

### 7.9 退化触发空间分布 (N1, 必做)

**目的**: 触发率 30% 可能是走廊段集中触发, 也可能是全程随机抖动. 论文必须证明前者.
本节用 [OdomFrame] 逐帧日志 + 改进版轨迹, 画出退化触发点的空间分布.

**前提**: §7.4 / §7.5 回放时已经把 FAST-LIO 终端输出 tee 到 `fastlio_improved.log` /
`fastlio_always.log` (与 §7.6 触发率提取共用同一份日志, 不需额外采集).

`evaluate_slam.sh` 阶段 6 会自动生成:

- `results/degradation_spatial_improved.png` — 改进版 (退化感知)
- `results/degradation_spatial_always.png` — 常开强约束 (若有)

每张图含:
- 灰色折线: 该组的 SLAM XY 轨迹
- 蓝色小点: 正常帧 (`deg=0`) 的当前位置
- 红色大点: 退化帧 (`deg=1`) 的当前位置
- 标题: `<label>: degradation spatial distribution (X.X% triggered)`

**期望结果**:
- 改进版: 红点应**集中在长廊段**, 室内开阔段几乎无红点 → 创新点真正在该激活的位置激活.
- 常开版: 整条轨迹都是红点 (`force_degraded=true` 强制 100% 退化), 用作"红点全覆盖"对照.

**判读细则**:
- 若改进版红点零散分布在整条轨迹: 退化判据**对噪声过于敏感**, 调高 `degradation_residual_threshold` 重跑.
- 若长廊段也几乎没有红点但闭环漂移仍下降: 创新基本不参与, 漂移降低来自常开弱约束 — 论文立论失败.
- 红点边界 (走廊出入口) 是论文里**最有说服力**的视觉证据, 截图时尽量保留环境平面图叠加.

> **要求**: 若 `[OdomFrame]` 行不存在, 说明 FAST-LIO 是旧二进制. 重新 `colcon build --packages-select fast_lio`
> 后再回放即可. 该日志只在 `odom_constraint:=true` 时输出, baseline 不会有.

### 7.10 退化阈值敏感性扫描 (N2, 必做)

**目的**: 论文若直接报告 `feat=200 / res=0.15` 的结果, 等于"调一次就发表", 缺少阈值鲁棒性分析.
本节用同一段退化 bag 跑 3×3 阈值网格, 证明改进算法对阈值不敏感.

**网格**:
- `feat ∈ {100, 200, 400}` — `degradation_feat_threshold`
- `res ∈ {0.10, 0.15, 0.25}` — `degradation_residual_threshold`
- 共 9 次回放, 每次 ~10 min, 总计约 1.5 h.

**采集流程** (复用 §7.4 改进版回放):

```bash
SWEEP_ROOT=~/go1_ws/trajectories/threshold_sweep
mkdir -p ${SWEEP_ROOT}

for FEAT in 100 200 400; do
  for RES in 0.10 0.15 0.25; do
    SUB=${SWEEP_ROOT}/feat${FEAT}_res${RES}
    mkdir -p ${SUB}
    # 终端1: 改进版回放, 通过 ROS 参数覆盖阈值
    ros2 launch go1_bringup go1_replay.launch.py odom_constraint:=true 2>&1 | tee ${SUB}/fastlio_improved.log &
    LIO_PID=$!
    sleep 2
    # 改写阈值参数 (mid360.yaml 默认 200/0.15, 这里覆盖)
    ros2 param set /laserMapping odom_constraint.degradation_feat_threshold ${FEAT}
    ros2 param set /laserMapping odom_constraint.degradation_residual_threshold ${RES}
    # 终端2: 录轨迹 + 喂 bag
    ros2 run go1_bringup record_trajectory --ros-args -p experiment_label:=improved \
        -p output_dir:=${SUB} &
    REC_PID=$!
    ros2 bag play <degradation_bag> --clock
    kill ${REC_PID} ${LIO_PID}
  done
done
```

> 上面循环只是骨架, 实际操作建议手动逐组跑并核对每段 bag 完整回放, 防止 `--clock` 因时间错位静默失败.
> 阈值参数也可以直接编辑 `FAST_LIO/config/mid360.yaml` 后 colcon build 重启, 更稳定但慢.

**汇总** (新增工具脚本):

```bash
ros2 run go1_bringup threshold_sensitivity ${SWEEP_ROOT}
# 输出:
#   ${SWEEP_ROOT}/sensitivity_summary.csv   每行 (feat, res, 触发率, 闭环漂移, 轨迹长度)
#   ${SWEEP_ROOT}/sensitivity_summary.md    3x3 markdown 表 (论文直接用)
```

**判读**:
- 触发率 20%-60% 的格子是"可用工作点", 论文里画一个绿色框圈出.
- 同一 `res` 下沿 `feat` 升降, 触发率应单调上升; 反之亦然 — 验证判据物理意义.
- 闭环漂移在可用工作点附近应大致稳定 (变化 < 30%), 否则说明算法对阈值过于敏感, 工程价值弱.

### 7.11 静止启动守卫消融 (R2, 推荐)

**目的**: [algorithm_design.md §7.5](algorithm_design.md) 的"静止启动守卫"目前只有代码, 没有专门实验.
答辩老师会问"如果上电就走会怎么样?", 需要可量化回答.

**两组对照** (同一退化路线, 各录 1 段 bag):

| 组别 | 启动姿势 | 预期 |
|------|----------|------|
| `bag_walk_immediately` | 启动 FAST-LIO 后 < 0.5 s 立即遥控前进 | 首帧对齐发生在 LIO 未收敛时, 改进版退化段出现 ~0.1-0.15 m 系统性偏置 |
| `bag_stand_then_walk` | 启动后机器人静立 ≥ 1 s, 待 [OdomConstraint] INFO 打印 SE(2) 对齐, 再遥控 | 偏置消失, 漂移与守卫设计预期一致 |

两段 bag 用 §7.4 改进版回放, 按 §7.6 出闭环漂移, 论文里以 1 段 100 字内的"鲁棒性说明"展示守卫前后差异.
若两组漂移差异 < 5 cm, 说明守卫已自动覆盖该风险, 论文照实写; 若差异显著, 论文中保留这段对照作为
"启动操作建议".

## 8. 实验五：SLAM 轨迹精度评估

> **目标**: 使用 evo 工具和辅助脚本分析消融实验结果  
> **前提**: 已完成实验四，生成了 `traj_fastlio_baseline.txt`、`traj_fastlio_improved.txt`
> 和可选的 `traj_fastlio_always.txt`

### 8.1 评估指标说明

> **重要**: 本项目不具备 mm 级绝对真值（动捕/RTK-GPS），因此**不使用 APE（绝对位姿误差）**。
> 用 baseline 当"参考"算出来的 APE 不是真正的绝对精度，不应出现在论文中。

| 指标 | 含义 | 是否需要真值 | 论文用途 |
|------|------|:---:|----------|
| **平面闭环漂移** | 闭合回路首尾 XY 位移差 (m) | 否 | **核心定量指标**，直接反映平面累积漂移 |
| **漂移率** | 平面闭环漂移 / 轨迹总长 x 100% | 否 | 归一化后可跨实验对比 |
| **已知几何误差** | SLAM 量出的距离 vs 卷尺实测 (m / %) | 否 | 验证退化段的尺度漂移 |
| **轨迹一致性 RPE** | 两种算法局部运动差异 (m) | 否 | 在退化段 RPE 大 = 两种方法差异大 |
| **地图质量对比** | 建图结果的视觉一致性 | 否 | 定性分析，退化段的形变/错位 |

### 8.2 手动使用 evo 命令

```bash
# 1. 绘制两条轨迹的俯视图对比 (用于论文配图 + 读取坐标填 geometry_constraints.csv)
#    ROS REP-103 俯视图是 XY 平面 (不是 XZ, 见 §7.2 提示)
evo_traj tum \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_improved.txt \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_always.txt \
    -p --plot_mode xy

# 2. 计算两条轨迹的一致性 RPE (每 1m 一段)
#    含义: 正常段两条轨迹运动一致, RPE 小; 退化段 baseline 漂移, RPE 大
evo_rpe tum \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_improved.txt \
    -va --delta 1 --delta_unit m
```

### 8.3 已知几何距离误差测量

这是本项目在无动捕条件下获取"半定量真值"的核心方法:

**步骤一**: 用卷尺量几个关键距离（走廊长度、房间宽度、两柱间距等），精度到 cm

**步骤二**: 跑一次 SLAM 后用 `evo_traj --plot_mode xy` 画俯视图，读出对应位置的大致 (x, y)

**步骤三**: 写入约束文件
```bash
cat > ~/go1_ws/trajectories/geometry_constraints.csv << 'EOF'
# 标签, 实测距离(m), 起点x, 起点y, 终点x, 终点y
走廊长度,30.50,1.20,0.35,31.05,1.80
房间A宽度,6.00,-0.50,0.10,-0.50,6.05
柱间距,3.20,5.00,2.00,8.15,2.10
EOF
```

**步骤四**: 运行测量脚本
```bash
# 基线
ros2 run go1_bringup measure_geometry \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/degradation_exp1/results/geometry_baseline.csv

# 改进版
ros2 run go1_bringup measure_geometry \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_improved.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/degradation_exp1/results/geometry_improved.csv

# 常开强约束（若已采集）
ros2 run go1_bringup measure_geometry \
    ~/go1_ws/trajectories/degradation_exp1/traj_fastlio_always.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/degradation_exp1/results/geometry_always.csv
```

> **建议**: 至少准备 3-5 组约束；走廊纵向距离最有价值（baseline 在此方向漂移最严重）。

### 8.4 论文图表建议

需要准备的图表：

1. **退化路线轨迹俯视对比图**（baseline / 退化感知 / 常开强约束，标注退化段）
2. **非退化路线轨迹俯视对比图**（证明改进版正常场景不劣化）
3. **平面闭环漂移柱状图**（退化与非退化各 3 次重复，含误差棒）
4. **已知几何误差对比表**（每组约束的 baseline / improved / always-on 误差百分比）
5. **退化检测日志截图**（7.7 的 WARN 日志，佐证退化检测有效性）
6. **建图质量对比**（PCD 切片生成的 2D 栅格地图截图，baseline 形变 vs improved 保持一致；
   或直接对比两次 FAST-LIO `scans.pcd` 的 3D 点云俯视图）
7. **评估指标汇总表**（退化/非退化、3 次实验均值 +/- 标准差）

> **不要放 APE 图/表**: 没有真值的 APE 在答辩时容易被问"你的 ground truth 从哪来？"
> 平面闭环漂移 + 已知几何误差在方法论上站得住脚。

| `path_length_m` | trial 期间 `/Odometry` 累积路径长度 (米) |
| `goal_x/y/yaw` | 最近一次 `/goal_pose` 的目标坐标 |
| `cmd_samples` | trial 内收到的 `/cmd_vel` 样本数 |
| `cmd_linear_peak_mps` | 平面线速度峰值 `sqrt(vx²+vy²)` |
| `cmd_angular_peak_radps` | 角速度峰值 `abs(wz)` |
| `cmd_linear_delta_mean/max_mps` | 相邻 `/cmd_vel` 平面线速度向量变化均值/最大值，越小越平滑 |
| `cmd_angular_delta_mean/max_radps` | 相邻 `/cmd_vel` 角速度变化均值/最大值，越小越平滑 |
| `cmd_linear_accel_peak_mps2` | 按接收时间估算的线速度变化峰值，近似反映急加减速 |
| `cmd_angular_accel_peak_radps2` | 按接收时间估算的角速度变化峰值，近似反映急转向 |

逐帧 `/cmd_vel` CSV 字段：

| 字段 | 含义 |
|------|------|
| `trial_id` | 对应主 CSV 的 trial 编号 |
| `stamp_s` | `nav_metrics` 接收 `/cmd_vel` 的节点时间 |
| `vx_mps / vy_mps / wz_radps` | `/cmd_vel` 原始速度命令 |
| `linear_speed_mps` | 平面线速度模长 |
| `angular_abs_radps` | 角速度绝对值 |

> **说明**: `status` 为 `ABORTED` 常见原因是全局规划失败或控制器超时；
> `CANCELED` 通常是用户在 RViz 点击了 "Cancel" 或通过 `/goal_pose` 发了新目标。

### 10.7 velocity_smoother

ROS2 Humble 的 `nav2_bringup/navigation_launch.py` 会把 `controller_server` 的
`cmd_vel` remap 到 `cmd_vel_nav`, 再把 `velocity_smoother` 的 `cmd_vel_smoothed`
remap 回 `/cmd_vel`. 因此本项目中 `velocity_smoother` **不是空跑**, 而是 Nav2

否则默认参数会把 `vy` 限为 0, 与 TEB 的 `holonomic_robot: true` 冲突。

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `smoothing_frequency` | 20.0 | 平滑输出频率 (Hz) |
| `feedback` | `OPEN_LOOP` | 不依赖 10Hz FAST-LIO 速度反馈, 避免延迟引入振荡 |
| `max_velocity` | `[0.3, 0.2, 0.7]` | 与 TEB `max_vel_*` 保持一致 |
| `min_velocity` | `[-0.15, -0.2, -0.7]` | X 后退限速与 `max_vel_x_backwards` 一致 |
| `max_accel` | `[0.8, 0.8, 1.5]` | 与 TEB `acc_lim_*` 保持一致 |
| `max_decel` | `[-0.8, -0.8, -1.5]` | 与 TEB 减速能力匹配 |

## 12. TF 坐标系关系图

**关键设计**: FAST-LIO 子树与 unitree_ros 子树**互不相交**。两者的根分别是
`camera_init` 和 `unitree_odom`, 没有 TF 桥接. `body` 与 `unitree_base`
在工程上近似同一机体中心, 但不通过 TF 连起来 — 以前用 `unitree_base → body` 身份桥接会
造成 `body` 双父冲突 (`TF_REPEATED_DATA` 警告, 位姿查询时序相关), 现已移除.
EKF 完全在 unitree 子树内工作, 其输出 `/odometry/filtered` 使用
`unitree_odom → unitree_base` 帧名, 但不发布 TF. FAST-LIO 的 `odom_constraint`
按**消息内容**读取这个位置, 首帧做 `unitree_odom` 到 `camera_init` 的 SE(2)
初始平面对齐, 后续使用腿部里程计的平面位移增量, 不依赖跨树 TF.

```
                    ┌──────────────────────────────────────────┐
                    │               TF 树结构 (两棵子树)         │
                    └──────────────────────────────────────────┘

  FAST-LIO 子树 (一直存在)              unitree_ros 子树 (一直存在)
  ────────────────────────              ─────────────────────────
  [map]                                  [unitree_odom]
    │                                       │
    │ (AMCL 发布, 仅 Nav2 模式)              │ (unitree_ros 发布, ~50-100Hz)
    ↓                                       ↓
  [camera_init]                          [unitree_base]
    │                                       │
    │ (FAST-LIO2 发布, ~10Hz)                │ (静态TF, 身份变换,
    ↓                                       │  仅 use_odom_fusion:=true,
  [body]                                    │  让 EKF 能把 /imu 变换到
    │                                       │  base_link_frame=unitree_base)
    │ (静态TF, go1_base.launch.py,          ↓
    │  实机需测量并修改 — 见 §4.5)           [imu]
    ↓
  [livox_frame]


  数据流 (MID-360S):
  ┌───────────────────────────────────────────────────────────────────────┐
  │ LiDAR (/livox/lidar) ──→ FAST-LIO2 ──→ /Odometry, /cloud_registered │
  │ IMU   (/livox/imu)   ──→            ──→ TF: camera_init → body       │
  │                                                                       │
  │ [EKF 仅在 use_odom_fusion:=true 时激活]                                 │
  │ Odom  (/odom, frame=unitree_odom→unitree_base) ──→ robot_localization │
  │ IMU   (/imu,  frame=imu)                       ──→ (EKF融合)          │
  │ → /odometry/filtered (frame=unitree_odom→unitree_base, 不发布TF)      │
  │ → FAST-LIO2 odom_constraint 首帧SE(2)对齐后读取平面位移 (需 enable_odom_constraint)│
  │                                                                       │
  │ /cloud_registered    ──→ pointcloud_to_laserscan ──→ /scan           │
  │ /scan                ──→ Nav2 ─→ /cmd_vel_nav ─→ smoother ─→ /cmd_vel│
  └───────────────────────────────────────────────────────────────────────┘
```

| `/cmd_vel` | Twist | velocity_smoother/遥控 | - | 发送给 unitree_ros 的最终速度指令 |
| `/livox/lidar` | CustomMsg | livox_driver | 10Hz | MID-360S 原始点云 |
| `/livox/imu` | Imu | livox_driver | 200Hz | MID-360S IMU |
| `/Odometry` | Odometry | FAST-LIO2 | 10Hz | LiDAR-IMU 里程计 |
| `/cloud_registered` | PointCloud2 | FAST-LIO2 | 10Hz | 去畸变点云 |
| `/odometry/filtered` | Odometry | robot_loc | 50Hz | 融合里程计 (odom_fusion) |
| `/scan` | LaserScan | pc2scan | 10Hz | 2D 激光扫描 |
| `/map` | OccupancyGrid | nav2_map_server | latched | 栅格地图 (导航阶段, 来自 PCD 切片) |

### 13.2 Launch 命令速查

```bash
# 基础模式 (不含里程计融合)
ros2 launch go1_bringup go1_base.launch.py use_odom_fusion:=false

# EKF 模式 (只启动 robot_localization, FAST-LIO 默认不使用该约束)
ros2 launch go1_bringup go1_base.launch.py use_odom_fusion:=true

# 在线改进模式 (EKF + FAST-LIO 退化场景 odom 约束)
ros2 launch go1_bringup go1_base.launch.py \
    use_odom_fusion:=true \
    enable_odom_constraint:=true

# 建图 (基础模式)
ros2 launch go1_bringup go1_mapping.launch.py use_odom_fusion:=false

# 导航 (基础模式)
ros2 launch go1_bringup go1_nav.launch.py use_odom_fusion:=false

# 消融实验 — 基线回放

# 消融实验 — 融合回放
ros2 launch go1_bringup go1_replay.launch.py odom_constraint:=true

# 消融实验 — 常开强约束回放
ros2 launch go1_bringup go1_replay.launch.py odom_constraint:=true force_degraded:=true
```

## 附录 C：紧急回退方案

### TEB 无法编译 -> 回退到 RPP 控制器

修改 `go1_nav_params.yaml`：
```yaml
FollowPath:
  plugin: "nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController"
  desired_linear_vel: 0.3
  lookahead_dist: 0.6
  min_lookahead_dist: 0.3
  max_lookahead_dist: 0.9
  lookahead_time: 1.5
  rotate_to_heading_angular_vel: 1.0
  transform_tolerance: 0.1
```
> 注意: RPP 不支持全向运动，Go1 只能前进和原地旋转

### robot_localization 无法安装 -> 使用基础模式

```bash
# 所有 launch 命令添加 use_odom_fusion:=false
ros2 launch go1_bringup go1_nav.launch.py use_odom_fusion:=false
```

消融实验需要 robot_localization，此时无法进行融合对比实验。

```bash
# 查看原始 3D 点云 (需要 pcl-tools: sudo apt install pcl-tools)
```
