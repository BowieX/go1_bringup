### 4.5 LiDAR → body 外参测量（**实机部署必做**）

> **目标**: 测量 MID-360S 相对 Go1 机体的安装位置，并写入 launch 文件。  
> **重要性**: 外参是 SLAM 精度的基础，误差 >2cm 会直接反映到点云错位和地图扭曲。

#### 4.5.1 坐标系约定

遵循 ROS REP-103：
- `body` 帧原点 = 机器狗腰部几何中心（四腿投影中心点，水平面的机体中线交点）
- `livox_frame` 帧原点 = **MID-360S 外壳底部**（Livox 手册标注的传感器坐标系原点，不是外壳几何中心）
- 两帧的坐标轴方向一致：**X 前、Y 左、Z 上**

> ⚠️ 常见误区：Livox MID-360 系列的 frame 原点是**雷达外壳底面**，不是外壳几何中心。若按外壳中心测量会系统性偏高约 3 cm。

#### 4.5.2 测量步骤

让机器狗站立在水平地面、**头朝前**。

**Z 偏移（垂直方向，最关键）**：
- 直接可测方案：用卡尺/直尺测 "LiDAR 外壳**底面** ↔ 机体腰部中心" 的垂直距离即为 `z`
- 腰部中心不可直接触及时，可通过 `(背部顶面到地 + 腹部底面到地) / 2` 估算腰部中心高度 `h_body`，再用 `z = h_lidar_bottom - h_body`
- Go1 站姿下 `h_body` 约 0.28–0.32 m

**X 偏移（前后方向）**：
1. 找到机身前后中线（左右两前髋 / 左右两后髋中点连线交汇处）
2. 从机身中心垂直于地面画一条参考线，测 LiDAR 底部中心到这条线的水平距离
3. LiDAR 在机身**前方** → `x` 为**正**；在后方 → 负

**Y 偏移（左右方向）**：
1. 找机身左右中线（两前腿或两后腿投影中点连线）
2. 测 LiDAR 底部中心到中线的水平距离
3. LiDAR 偏向**左侧** → `y` 为**正**；偏向右 → 负

**姿态（roll / pitch / yaw）**：
- 绝大多数夹具是水平固定 → 三个角都 = `0.0`
- 若 LiDAR 朝下倾斜（抬地面感知）：用量角器测倾角 `α°`（度），`pitch = -α × π / 180`（弧度，向下倾为负）
- 若 LiDAR 偏向一侧安装（Y 轴转角）：测 yaw 角，单位弧度

#### 4.5.3 当前实测值（2026-04-17）

```
x =  0.008   m   (LiDAR 在机身前方 8 mm)
y =  0.000   m   (居中，无左右偏移)
z =  0.2742  m   (LiDAR 外壳底部比腰部中心高 274.2 mm)
yaw = pitch = roll = 0.0  (水平夹具安装)
```

这组值已写入两个 launch 文件（见 §4.5.4）。如更换安装方式必须重新测量并同步修改两处。

#### 4.5.4 修改代码

同步修改**两处** launch 文件（文件名见注释的 TODO(实机) 标记）：

1. [go1_bringup/launch/go1_base.launch.py](../launch/go1_base.launch.py) 的 `lidar_tf` 节点
2. [go1_bringup/launch/go1_replay.launch.py](../launch/go1_replay.launch.py) 的 `lidar_tf` 节点

```python

    '--x', '0.008',    # 实测 x (m)
    '--y', '0.000',    # 实测 y (m)
    '--z', '0.2742',   # 实测 z (m)
    '--yaw',   '0.0',  # 夹具无偏转时保持 0
```

#### 4.5.5 验证外参

```bash

# 终端2: 查看 body->livox_frame TF
```

## 5. 实验二：SLAM 建图（FAST-LIO 在线建图 + PCD 离线切片）

> **目标**: 生成 Nav2 可用的 2D 占据栅格地图，供后续导航使用  
> **前提**: 实验一硬件验证通过

### 5.0 路线选择说明（为什么不用 slam_toolbox）

项目原先采用 `slam_toolbox`（2D 扫描匹配 + Karto 图优化）实时生成栅格地图。
实验中发现：Go1 的高频 Z 轴颠簸 + Pitch 俯仰抖动会让 `pointcloud_to_laserscan`
输出的 2D 扫描畸变；在长廊等几何退化场景下，slam_toolbox 扫描匹配的旋转约束
很弱，**走 8 字型路径二次经过同一位置时会出现明显角度偏差**（重影 / 错位）。

而 FAST-LIO 同时融合 IMU + LiDAR，ikd-Tree 增量子地图的 3D 点云质量明显更高，
**肉眼检查即能确认 3D 地图无明显漂移**。

因此项目采用 **路线 B**：
1. 在线阶段：只跑 FAST-LIO，启用 `pcd_save_en` 累积全局 3D 点云；
2. 离线阶段：用 `pcd_to_map.py` 把 PCD 在 Go1 腰部以下高度带切片，栅格化为
   Nav2 标准 `pgm + yaml`；
3. Nav2 栈（map_server / AMCL / Planner / Controller）**一字不改**照常加载。

### 5.6 离线切片生成 2D 地图

```bash
python3 ~/go1_ws/src/go1_bringup/scripts/pcd_to_map.py \
    ~/go1_ws/src/FAST_LIO/PCD/scans.pcd \
    ~/go1_ws/src/go1_bringup/maps \
    my_lab \
    --z-min 0.05 --z-max 0.25 \
    --resolution 0.05 \
    --hit-threshold 2 \
    --padding 0.5
```

参数说明（位于 map 坐标系，即 FAST-LIO 的 `camera_init` 帧，Z 以地面为 0）：

| 参数 | 含义 | 调优建议 |
|------|------|----------|
| `--z-min / --z-max` | 切片高度带（米） | 默认 `[0.05, 0.25]`（Go1 膝关节以下）。若实验室有低矮障碍（≤ 5 cm）漏掉，可下探到 0.02；若地面凹凸大导致地面被当墙，提高 `z-min` |
| `--resolution` | 栅格分辨率（米/格） | 默认 0.05，与 Nav2 costmap 默认一致 |
| `--hit-threshold` | 单格需累计多少次命中才算占据 | 默认 2，降噪；若稀疏场景漏墙调到 1；稠密噪点多调到 5 |
| `--padding` | bbox 外扩（米） | 防止地图紧贴点云边界；Nav2 做路径规划时机器人需要至少 inflation_radius 的自由空间 |

输出：
- `my_lab.pgm` — P5 灰度图（0=占据, 254=空闲, 205=未知）
- `my_lab.yaml` — Nav2 `map_server` 标准元数据

脚本会输出栅格尺寸、占据/空闲格子数、`origin` 世界坐标。典型值：
```
[1/4] 加载 PCD: .../scans.pcd (752.5 MB)
        读取 23,514,482 个点, Z 范围 [-4.441, 13.365]
[2/4] Z 切片 [0.05, 0.25] + 栅格化 (res=0.05 m)
        尺寸 672x1013, 占据 18,982 格, 空闲 661,754 格
        origin (世界坐标, 左下角): (-8.080, -13.279)
```

**问题：导航一开始就报 "Failed to get a plan"**

```
解决：
```

```
    holonomic_robot: true
    weight_kinematics_nh: 0.0
    max_vel_y: 0.3  (必须 > 0)
```

**问题：Plugin "teb_local_planner::TebLocalPlannerROS" not found**
```
原因：TEB 未编译成功或未正确安装
解决：
  1. colcon build --packages-select teb_local_planner
  2. source install/setup.bash
  3. ros2 plugin list | grep teb （确认插件已注册）
```

## 7. 实验四：SLAM 消融实验（足端里程计融合验证）

> **目标**: 通过 rosbag 离线回放，在完全相同的传感器输入下，对比加入/不加入足端里程计融合对 SLAM 精度的影响  
> **前提**: 实验一硬件验证通过

### 7.1 消融实验方法论

**为什么用 rosbag 离线回放？**

| 方案 | 优势 | 劣势 |
|------|------|------|
| 在线两次实跑 | 简单 | 无法保证路线完全一致，不公平 |
| **rosbag 离线回放** | 完全相同的输入数据，严格可复现 | 需要 `use_sim_time` 配置 |
| 导航层消融 | 验证端到端效果 | 变量太多，不适合单一因子消融 |

**实验变量**: 唯一变量是 `odom_constraint.enable`（开/关），其余所有参数和输入数据完全相同。

**场景要求**: 包含几何退化段（走廊）的闭环路线。

### 7.2 数据采集（在真机上）

设计一个包含退化段的闭环路线：
```
[起点/终点: 教室A] -> [走廊(退化段, 30m+)] -> [教室B] -> [走廊返回] -> [教室A]
```

**步骤一: 测量已知几何距离**

在采集数据**之前**，用卷尺测量实验场地中的几个关键距离，记录到 CSV 文件中。
这些数据将作为 SLAM 精度的"已知几何约束"参考:

```bash
# 创建约束文件 (示例，请根据实际场地修改)
cat > ~/go1_ws/trajectories/geometry_constraints.csv << 'EOF'
# 标签, 实测距离(m), 起点x, 起点y, 终点x, 终点y
# 注意: 起点/终点坐标是 SLAM 轨迹中的大致坐标, 首次先空着,
#       跑完第一次 SLAM 用 evo_traj 俯视图读取后再填入
走廊长度,30.5,0.0,0.0,0.0,0.0
房间A对角线,8.2,0.0,0.0,0.0,0.0
房间B宽度,6.0,0.0,0.0,0.0,0.0
EOF
```

> **提示**: 起点/终点的坐标需要跑完第一次 SLAM 后, 用 `evo_traj --plot_mode xz`
> 画俯视图, 读出对应位置的大致 (x, y) 坐标后回填。首次运行评估脚本时
> 如果没有此文件会自动跳过, 不影响闭环漂移的计算。

**步骤二: 录制传感器数据**

`go1_base.launch.py` 现在**默认自动录制 rosbag**（见 §5.1），只需启动并走完即可：

```bash
# 终端 1: 启动底层驱动 + FAST-LIO2 + 自动 rosbag 录制
ros2 launch go1_bringup go1_base.launch.py \
    use_odom_fusion:=false \
    bag_dir:=$HOME/go1_ws/bags/degradation_exp1

# 用遥控器控制机器人沿预定路线行走
# 走完闭环后 Ctrl+C 停止录制, bag 保存在 bag_dir/<时间戳>/
```

**重复 3 次**，每次传入不同 `bag_dir`：
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp1`
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp2`
- `bag_dir:=$HOME/go1_ws/bags/degradation_exp3`

> **关键提醒**:
> - 起点和终点必须尽量重合（计算闭环漂移的前提）
> - 走廊段至少 30m 以确保几何退化发生
> - 行走速度保持 0.2-0.3 m/s，与正常工况一致
> - 录制时只录原始传感器话题，不录算法输出话题

### 7.3 离线回放 — 基线实验（无融合）

对每个 rosbag 执行：

```bash
# 终端1: 启动 FAST-LIO2 (无里程计约束，use_sim_time 自动启用)
ros2 launch go1_bringup go1_replay.launch.py odom_constraint:=false

# 终端2: 启动轨迹记录 (experiment_label 自动命名为 traj_fastlio_baseline.txt)
python3 ~/go1_ws/src/go1_bringup/scripts/record_trajectory.py --ros-args \
    -p use_sim_time:=true \
    -p output_dir:=$HOME/go1_ws/trajectories \
    -p record_mode:=fastlio \
    -p experiment_label:=baseline

# 终端3: 回放 rosbag (自动录制的 bag 在 degradation_exp1/<时间戳>/ 下)
# 取最近一次录制: ls -td ~/go1_ws/bags/degradation_exp1/*/ | head -1
BAG=$(ls -td ~/go1_ws/bags/degradation_exp1/*/ | head -1)
ros2 bag play "$BAG" --clock --topics /livox/lidar /livox/imu /odom /imu

# 等待回放结束（终端3自动退出），然后 Ctrl+C 终端1和终端2
```

输出文件: `~/go1_ws/trajectories/traj_fastlio_baseline.txt`

### 7.4 离线回放 — 融合实验（有足端里程计约束）

用**同一个 rosbag** 再回放一次：

```bash
# 终端1: 启动 FAST-LIO2 + robot_localization EKF (开启里程计约束)
# 注意: 用 tee 把终端日志写到文件, 供 evaluate_slam.sh 提取退化触发率 ([OdomStat] 行)
ros2 launch go1_bringup go1_replay.launch.py odom_constraint:=true \
    2>&1 | tee $HOME/go1_ws/trajectories/fastlio_improved.log

# 终端2: 启动轨迹记录 (experiment_label 自动命名为 traj_fastlio_improved.txt)
python3 ~/go1_ws/src/go1_bringup/scripts/record_trajectory.py --ros-args \
    -p use_sim_time:=true \
    -p output_dir:=$HOME/go1_ws/trajectories \
    -p record_mode:=fastlio \
    -p experiment_label:=improved

# 终端3: 回放同一 rosbag (与 7.3 相同)
BAG=$(ls -td ~/go1_ws/bags/degradation_exp1/*/ | head -1)
ros2 bag play "$BAG" --clock --topics /livox/lidar /livox/imu /odom /imu

# 等待回放结束，Ctrl+C 停止
```

输出文件:
- `~/go1_ws/trajectories/traj_fastlio_improved.txt` — 轨迹
- `~/go1_ws/trajectories/fastlio_improved.log` — FAST-LIO 终端日志 (含 [OdomStat] 触发率汇报)

### 7.5 运行评估

```bash
chmod +x ~/go1_ws/src/go1_bringup/scripts/evaluate_slam.sh
~/go1_ws/src/go1_bringup/scripts/evaluate_slam.sh ~/go1_ws/trajectories
```

评估脚本会自动输出：
- **闭环漂移对比** — 核心定量指标
- **已知几何距离误差** — 需要 `geometry_constraints.csv`（可选，首次可跳过）
- **轨迹俯视对比图** — 定性对比
- **轨迹一致性 RPE** — 衡量两种方法的局部行为差异
- 汇总表（可直接用于论文）

> **注意**: 本脚本不计算 APE（绝对位姿误差）。APE 需要 mm 级绝对真值
> （动捕/RTK），本项目不具备此条件。用 baseline 当"参考"算出来的 APE
> 不是真正的绝对精度，论文中不应使用。

### 7.7 观察退化检测日志与触发率

在融合实验的回放过程中（终端1），注意观察两类关键日志：

**1. 退化事件 WARN (每个退化瞬间都会打印, 节流 2 秒)**:
```
[WARN] Geometric degradation detected! feat_num=132, res_mean=0.172. Applying odom constraint with high weight.
```
这说明走廊段被正确识别为退化区域，足端里程计约束被激活。

**2. 统计汇报 INFO (每 100 帧一次, 由 evaluate_slam.sh 自动提取)**:
```
[INFO] [OdomStat] degraded=157/500 (31.4%), feat_num=412, res_mean=0.082
```
这条日志里的百分比就是**退化触发率** — 评估创新是否真正生效的关键指标。

> ⚠️ **关键验证 — 触发率必须 > 0 且在合理区间**
>
> 若 `evaluate_slam.sh` 阶段 5 显示触发率接近 0%:
> - 说明**退化判据从未触发**, "改进版"实际上全程用 `odom_noise_normal=10` 运行, 与基线的
>   漂移差距几乎全部来自"常开弱约束"的微弱效果, 论文立论站不住脚。
> - **排查路径**: 降低 `degradation_feat_threshold` (如 200→100) 或
>   `degradation_residual_threshold` (如 0.15→0.10), 重新跑 §7.4 和 §7.5 评估。
>
> 若触发率 > 80%:
> - 说明阈值**过于宽松**, 改进版几乎全程强约束, 失去"仅退化时增强"的语义, 退化与正常场景无差异。
> - **排查路径**: 提高上述阈值重跑。
>
> **合理区间**: 20%-60% — 走廊段触发、室内开阔段不触发, 符合"选择性增强"的设计意图。
> 可跨 3 次实验查看方差，若波动过大需检查场地一致性。

> **提示**: 截图保存 `[WARN] Geometric degradation` 和 `[OdomStat]` 日志，作为论文中退化检测有效性的佐证。

## 8. 实验五：SLAM 轨迹精度评估

> **目标**: 使用 evo 工具和辅助脚本分析消融实验结果  
> **前提**: 已完成实验四，生成了 `traj_fastlio_baseline.txt` 和 `traj_fastlio_improved.txt`

### 8.1 评估指标说明

> **重要**: 本项目不具备 mm 级绝对真值（动捕/RTK-GPS），因此**不使用 APE（绝对位姿误差）**。
> 用 baseline 当"参考"算出来的 APE 不是真正的绝对精度，不应出现在论文中。

| 指标 | 含义 | 是否需要真值 | 论文用途 |
|------|------|:---:|----------|
| **闭环漂移** | 闭合回路首尾位置欧氏距离 (m) | 否 | **核心定量指标**，直接反映累积漂移 |
| **漂移率** | 闭环漂移 / 轨迹总长 x 100% | 否 | 归一化后可跨实验对比 |
| **已知几何误差** | SLAM 量出的距离 vs 卷尺实测 (m / %) | 否 | 验证退化段的尺度漂移 |
| **轨迹一致性 RPE** | 两种算法局部运动差异 (m) | 否 | 在退化段 RPE 大 = 两种方法差异大 |
| **地图质量对比** | 建图结果的视觉一致性 | 否 | 定性分析，退化段的形变/错位 |

### 8.2 手动使用 evo 命令

```bash
# 1. 绘制两条轨迹的俯视图对比 (用于论文配图 + 读取坐标填 geometry_constraints.csv)
evo_traj tum \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    -p --plot_mode xz

# 2. 计算两条轨迹的一致性 RPE (每 1m 一段)
#    含义: 正常段两条轨迹运动一致, RPE 小; 退化段 baseline 漂移, RPE 大
evo_rpe tum \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    -va --delta 1 --delta_unit m
```

### 8.3 已知几何距离误差测量

这是本项目在无动捕条件下获取"半定量真值"的核心方法:

**步骤一**: 用卷尺量几个关键距离（走廊长度、房间宽度、两柱间距等），精度到 cm

**步骤二**: 跑一次 SLAM 后用 `evo_traj --plot_mode xz` 画俯视图，读出对应位置的大致 (x, y)

**步骤三**: 写入约束文件
```bash

走廊长度,30.50,1.20,0.35,31.05,1.80
房间A宽度,6.00,-0.50,0.10,-0.50,6.05
柱间距,3.20,5.00,2.00,8.15,2.10
EOF
```

**步骤四**: 运行测量脚本
```bash
# 基线
python3 ~/go1_ws/src/go1_bringup/scripts/measure_geometry.py \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/results/geometry_baseline.csv

# 改进版
python3 ~/go1_ws/src/go1_bringup/scripts/measure_geometry.py \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/results/geometry_improved.csv
```

> **建议**: 至少准备 3-5 组约束；走廊纵向距离最有价值（baseline 在此方向漂移最严重）。

### 8.4 论文图表建议

需要准备的图表：

1. **轨迹俯视对比图**（evo_traj，baseline 蓝色 vs improved 红色，标注退化段）
2. **闭环漂移柱状图**（3 次重复实验，baseline vs improved，含误差棒）

6. **评估指标汇总表**（3 次实验均值 +/- 标准差）

> 闭环漂移 + 已知几何误差在方法论上站得住脚。

## 10. 参数调优指南

### 10.1 FAST-LIO2 里程计约束参数

文件: `~/go1_ws/src/FAST_LIO/config/mid360.yaml`

| 参数 | 默认值 | 合理区间 | 调整建议 |
|------|:---:|:---:|----------|
| `degradation_feat_threshold` | **200** | 50–500 | 开阔环境 `effct_feat_num` 正常值的 30-50%; FAST-LIO 典型正常 300-800 |
| `degradation_residual_threshold` | **0.15** | 0.05–0.30 | 正常场景 `res_mean_last` 通常 0.03-0.08, 取其 2-3 倍为阈值 |
| `odom_noise_normal` | 10.0 | 5.0–50.0 | 越大=正常时约束越弱(几乎不影响) |
| `odom_noise_degraded` | 0.1 | 0.01–1.0 | 越小=退化时约束越强 |
| `odom_timeout` | 0.5 | 0.3–2.0 | EKF 停发 > 此时长跳过约束, 防止 stale 数据拖偏滤波器 |

> **说明**: 原始 FAST-LIO PR 中 feat_threshold=50 / residual=0.3 在走廊场景实测**几乎不触发**，
> 会让改进版沦为"全程弱约束"。当前默认 (200 / 0.15) 针对室内走廊退化调高, 首次部署即可使用。

**调优闭环 (首次部署)**:

1. **测量 baseline**: 用 `runtime_pos_log_enable: true` 跑一段室内开阔环境（非走廊）,
   观察 FAST-LIO 终端里 `effect num` 与 `res_mean` 的**稳态范围**:
   ```bash
   # 在 mid360.yaml 临时改:
   #   runtime_pos_log_enable: true
   # 启动后观察 10-20 秒,  记录数值如: effect num 320-540, res_mean 0.04-0.09
   ```
2. **设阈值**:
   - `feat_threshold` = 稳态下限的 40-60% (如 320 × 0.5 = 160 → 取 150-200)
   - `residual_threshold` = 稳态上限的 2-3 倍 (如 0.09 × 2 = 0.18 → 取 0.15-0.20)
3. **跑消融实验**: `evaluate_slam.sh` 阶段 5 的触发率应落在 20%-60%;
   不在区间则回到第 2 步调整阈值。

## 11. 已知问题与 Bug 排查

### 11.1 TF 树冲突（最常见问题）

**症状**: 终端大量警告 `Warning: TF_REPEATED_DATA` 或 `Could not find a connection between...`

**排查步骤**：
```bash
# 1. 查看完整 TF 树
ros2 run tf2_tools view_frames
# 生成 frames.pdf，检查是否有重复的父子关系

# 2. 查看特定帧的变换
ros2 run tf2_ros tf2_echo map camera_init
ros2 run tf2_ros tf2_echo camera_init body
```

**常见冲突**:
- `robot_localization` 的 `publish_tf` 必须为 `false`（已配置）
- 使用 `use_odom_fusion:=false` 可完全规避融合相关的 TF 问题

### 11.2 时间戳不同步

**症状**: `Lookup would require extrapolation into the future`

**排查**:
```bash
# 查看各传感器时间戳是否接近
ros2 topic echo /odom --field header.stamp --once
ros2 topic echo /livox/lidar --field header.stamp --once
```

**解决**: 增大 `transform_tolerance`

### 11.3 FAST-LIO2 初始化失败

**症状**: 启动后终端一直输出 "No point, skip this scan!"

**解决**:
1. 确认 MID-360S 已通电并成功连接（检查网线/IP `192.168.1.135`）
2. 确认使用了正确的启动脚本 `msg_MID360s_launch.py`（不是 `msg_MID360_launch.py`）
3. 检查 `mid360.yaml` 中 `lid_topic` 和 `imu_topic` 是否正确（默认 `/livox/lidar` 和 `/livox/imu`）
4. FAST-LIO2 启动后前 2-3 秒输出此警告是**正常现象**（IMU 初始化），
   初始化完成后会输出 `IMU Initial Done` 并开始处理点云
5. 如果持续输出（超过 5 秒），检查 `/livox/lidar` 话题是否有数据：
   ```bash
   ros2 topic hz /livox/lidar
   ```

### 11.4 rosbag 回放相关问题

**症状**: 回放时 FAST-LIO2 不输出数据

**排查**:

```bash
# 确认使用了 --clock 和 --topics 参数

# 确认 FAST-LIO2 使用了 use_sim_time
ros2 param get /fastlio_mapping use_sim_time
```

**症状**: `/odometry/filtered` 无输出（fusion 模式回放）

**排查**:

## 附录 C：紧急回退方案

### TEB 无法编译 -> 回退到 RPP 控制器

修改 `go1_nav_params.yaml`：
```yaml
FollowPath:
  plugin: "nav2_regulated_pure_pursuit_controller::RegulatedPurePursuitController"
  desired_linear_vel: 0.3
  lookahead_dist: 0.6
  min_lookahead_dist: 0.3
  max_lookahead_dist: 0.9
  lookahead_time: 1.5
  rotate_to_heading_angular_vel: 1.0
  transform_tolerance: 0.1
```
> 注意: RPP 不支持全向运动，Go1 只能前进和原地旋转

### robot_localization 无法安装 -> 使用基础模式

```bash
# 所有 launch 命令添加 use_odom_fusion:=false
ros2 launch go1_bringup go1_nav.launch.py use_odom_fusion:=false
```

消融实验需要 robot_localization，此时无法进行融合对比实验。

### PCD 切片后地图质量差 -> 先肉眼检查 FAST-LIO 3D

```bash
# 查看原始 3D 点云 (需要 pcl-tools: sudo apt install pcl-tools)
pcl_viewer ~/go1_ws/src/FAST_LIO/PCD/scans.pcd

# 如果 3D 本身就漂 (墙有重影 / 长廊弯曲), 切片图必然也会漂 —— 先回去调 FAST-LIO
# 如果 3D 本身 OK 但 2D 图有问题, 尝试调整 pcd_to_map.py 的 --z-min/--z-max/--hit-threshold
```
