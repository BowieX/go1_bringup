### 4.4 验证遥控器控制

驱动节点启动后，机器人会站起来但遥控器**暂时无法**控制机器人行走。
这是因为驱动节点以 500Hz 持续发送 `STAND_UP` 指令，覆盖了遥控器的输入。

**激活遥控器**（必须执行）：在另一个终端手动发送一条零速度指令：
```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist '{}'
```
该指令将驱动模式从 `STAND_UP(6)` 切换到 `WALK_W_VEL(2)`，之后遥控器即可正常控制。

**验证遥控器已生效**：
```bash
# 用遥控器控制机器人行走，同时观察 /odom 数据变化
ros2 topic echo /odom --field pose.pose.position
# 推动遥控器摇杆，x/y 值应该变化
```

> **注意**: 每次重新启动 `unitree_driver_launch.py` 后都需要重新执行上述激活命令。
> 建图和导航的 launch 文件中包含了 `unitree_driver`，同样需要这一步。

### 4.5 LiDAR → body 外参测量（**实机部署必做**）

> **目标**: 测量 MID-360S 相对 Go1 机体的安装位置，并写入 launch 文件。  
> **重要性**: 外参是 SLAM 精度的基础，误差 >2cm 会直接反映到点云错位和地图扭曲。

#### 4.5.1 坐标系约定

遵循 ROS REP-103：
- `body` 帧原点 = 机器狗腰部几何中心（四腿投影中心点，水平面的机体中线交点）
- `livox_frame` 帧原点 = MID-360S 外壳几何中心（Livox 手册标注位置）
- 两帧的坐标轴方向一致：**X 前、Y 左、Z 上**

#### 4.5.2 测量步骤

让机器狗站立在水平地面、**头朝前**。

**Z 偏移（垂直方向，最关键）**：
1. 用直尺/卷尺测 LiDAR 外壳中心到地面的垂直高度 `h_lidar`（单位 m）
2. 测机体腰部中线到地面的高度 `h_body`（Go1 站姿约 0.28–0.32 m，需实测）
3. `z = h_lidar - h_body`

**X 偏移（前后方向）**：
1. 找到机身前后中线（左右两前髋 / 左右两后髋中点连线交汇处）
2. 从机身中心垂直于地面画一条参考线，测 LiDAR 中心到这条线的水平距离
3. LiDAR 在机身**前方** → `x` 为**正**；在后方 → 负

**Y 偏移（左右方向）**：
1. 找机身左右中线（两前腿或两后腿投影中点连线）
2. 测 LiDAR 中心到中线的水平距离
3. LiDAR 偏向**左侧** → `y` 为**正**；偏向右 → 负

**姿态（roll / pitch / yaw）**：
- 绝大多数夹具是水平固定 → 三个角都 = `0.0`
- 若 LiDAR 朝下倾斜（抬地面感知）：用量角器测倾角 `α°`（度），`pitch = -α × π / 180`（弧度，向下倾为负）
- 若 LiDAR 偏向一侧安装（Y 轴转角）：测 yaw 角，单位弧度

#### 4.5.3 示例（当前默认值对应的安装方式）

默认 `x=0.10, y=0.00, z=0.15`：
- LiDAR 在机身前方 10 cm
- 居中无左右偏移
- LiDAR 外壳中心比机体腰部中心高 15 cm（对应 `h_lidar ≈ 0.45m`、`h_body ≈ 0.30m`）

**这组值是示意值**，实机必须重测。

#### 4.5.4 修改代码

同步修改**两处** launch 文件（文件名见注释的 TODO(实机) 标记）：

1. [go1_bringup/launch/go1_base.launch.py](../launch/go1_base.launch.py) 的 `lidar_tf` 节点
2. [go1_bringup/launch/go1_replay.launch.py](../launch/go1_replay.launch.py) 的 `lidar_tf` 节点

#### 4.5.5 验证外参


## 5. 实验二：SLAM 建图（slam_toolbox）

> **目标**: 使用 slam_toolbox 生成 2D 占据栅格地图，供后续导航使用  
> **前提**: 实验一硬件验证通过

### 5.1 启动建图

```bash
# 基础导航 Demo 不需要里程计融合，使用 use_odom_fusion:=false
ros2 launch go1_bringup go1_mapping.launch.py use_odom_fusion:=false
```

这会启动：`unitree_ros` + `livox_driver`（MID-360S）+ `FAST-LIO2`（无odom约束）+ `pointcloud_to_laserscan` + `slam_toolbox`

> **注意**: 如果机器狗未开机，`unitree_driver` 节点会报错退出（`CONNECTION IS NOT AVAILABLE`），
> 但这**不影响**建图功能。LiDAR → FAST-LIO → pointcloud_to_laserscan → slam_toolbox 的数据链路
> 完全独立于机器狗驱动，建图仍然可以正常进行（需要手持/推车携带 LiDAR 遍历场地）。
>
> FAST-LIO2 启动后的前 2-3 秒会输出 `No point, skip this scan!` 警告，这是 IMU 初始化的正常现象，
> 初始化完成后会自动开始处理点云数据。

### 5.2 RViz 可视化建图过程

建图 launch 会 **自动启动 RViz2** 并加载预配置的可视化文件，无需手动操作。

自动加载的配置文件路径：`go1_bringup/config/go1_mapping.rviz`

已预配置的显示项：

| 显示项 | 话题 | 个性化设置 |
|--------|------|------------|
| **LaserScan** | `/scan` | 绿色点，像素大小 **5px** / 物理大小 0.05m，FlatColor 渲染 |
| **Map** | `/map` | 透明度 0.7，Draw Behind 启用 |
| **TF** | - | 所有坐标系，标尺 0.5 |
| **RegisteredCloud** | `/cloud_registered` | 橙色点云，像素大小 2px，透明度 0.6 |
| **Odometry** | `/Odometry` | 黄色箭头轨迹，保留 500 帧 |
| **Grid** | - | 1m 网格参考 |

## 7. 实验四：SLAM 消融实验（足端里程计融合验证）

> **目标**: 通过 rosbag 离线回放，在完全相同的传感器输入下，对比加入/不加入足端里程计融合对 SLAM 精度的影响  
> **前提**: 实验一硬件验证通过

### 7.1 消融实验方法论

**为什么用 rosbag 离线回放？**

| 方案 | 优势 | 劣势 |
|------|------|------|
| 在线两次实跑 | 简单 | 无法保证路线完全一致，不公平 |
| **rosbag 离线回放** | 完全相同的输入数据，严格可复现 | 需要 `use_sim_time` 配置 |
| 导航层消融 | 验证端到端效果 | 变量太多，不适合单一因子消融 |

**实验变量**: 唯一变量是 `odom_constraint.enable`（开/关），其余所有参数和输入数据完全相同。

**场景要求**: 包含几何退化段（走廊）的闭环路线。

### 7.2 数据采集（在真机上）

设计一个包含退化段的闭环路线：
```
[起点/终点: 教室A] -> [走廊(退化段, 30m+)] -> [教室B] -> [走廊返回] -> [教室A]
```

**步骤一: 测量已知几何距离**

在采集数据**之前**，用卷尺测量实验场地中的几个关键距离，记录到 CSV 文件中。
这些数据将作为 SLAM 精度的"已知几何约束"参考:

```bash
# 创建约束文件 (示例，请根据实际场地修改)
cat > ~/go1_ws/trajectories/geometry_constraints.csv << 'EOF'
# 标签, 实测距离(m), 起点x, 起点y, 终点x, 终点y
# 注意: 起点/终点坐标是 SLAM 轨迹中的大致坐标, 首次先空着,
#       跑完第一次 SLAM 用 evo_traj 俯视图读取后再填入
走廊长度,30.5,0.0,0.0,0.0,0.0
房间A对角线,8.2,0.0,0.0,0.0,0.0
房间B宽度,6.0,0.0,0.0,0.0,0.0
EOF
```

> **提示**: 起点/终点的坐标需要跑完第一次 SLAM 后, 用 `evo_traj --plot_mode xz`
> 画俯视图, 读出对应位置的大致 (x, y) 坐标后回填。首次运行评估脚本时
> 如果没有此文件会自动跳过, 不影响闭环漂移的计算。

**步骤二: 录制传感器数据**

```bash
# 终端1: 启动底层驱动 + FAST-LIO2 (数据采集不需要融合)
ros2 launch go1_bringup go1_base.launch.py use_odom_fusion:=false

# 终端2: 录制所有原始传感器数据
ros2 bag record /livox/lidar /livox/imu /odom /imu -o ~/go1_ws/bags/degradation_exp1

# 用遥控器控制机器人沿预定路线行走
# 走完闭环后 Ctrl+C 停止录制
```

**重复 3 次**，生成 3 个独立的 rosbag：
- `degradation_exp1`
- `degradation_exp2`
- `degradation_exp3`

> **关键提醒**:
> - 起点和终点必须尽量重合（计算闭环漂移的前提）
> - 走廊段至少 30m 以确保几何退化发生
> - 行走速度保持 0.2-0.3 m/s，与正常工况一致
> - 录制时只录原始传感器话题，不录算法输出话题

### 7.3 离线回放 — 基线实验（无融合）

## 8. 实验五：SLAM 轨迹精度评估

> **目标**: 使用 evo 工具和辅助脚本分析消融实验结果  
> **前提**: 已完成实验四，生成了 `traj_fastlio_baseline.txt` 和 `traj_fastlio_improved.txt`

### 8.1 评估指标说明

> **重要**: 本项目不具备 mm 级绝对真值（动捕/RTK-GPS），因此**不使用 APE（绝对位姿误差）**。
> 用 baseline 当"参考"算出来的 APE 不是真正的绝对精度，不应出现在论文中。

| 指标 | 含义 | 是否需要真值 | 论文用途 |
|------|------|:---:|----------|
| **闭环漂移** | 闭合回路首尾位置欧氏距离 (m) | 否 | **核心定量指标**，直接反映累积漂移 |
| **漂移率** | 闭环漂移 / 轨迹总长 x 100% | 否 | 归一化后可跨实验对比 |
| **已知几何误差** | SLAM 量出的距离 vs 卷尺实测 (m / %) | 否 | 验证退化段的尺度漂移 |
| **轨迹一致性 RPE** | 两种算法局部运动差异 (m) | 否 | 在退化段 RPE 大 = 两种方法差异大 |
| **地图质量对比** | 建图结果的视觉一致性 | 否 | 定性分析，退化段的形变/错位 |

### 8.2 手动使用 evo 命令

```bash
# 1. 绘制两条轨迹的俯视图对比 (用于论文配图 + 读取坐标填 geometry_constraints.csv)
evo_traj tum \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    -p --plot_mode xz

# 2. 计算两条轨迹的一致性 RPE (每 1m 一段)
#    含义: 正常段两条轨迹运动一致, RPE 小; 退化段 baseline 漂移, RPE 大
evo_rpe tum \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    -va --delta 1 --delta_unit m
```

### 8.3 已知几何距离误差测量

这是本项目在无动捕条件下获取"半定量真值"的核心方法:

**步骤一**: 用卷尺量几个关键距离（走廊长度、房间宽度、两柱间距等），精度到 cm

**步骤二**: 跑一次 SLAM 后用 `evo_traj --plot_mode xz` 画俯视图，读出对应位置的大致 (x, y)

**步骤三**: 写入约束文件
```bash
cat > ~/go1_ws/trajectories/geometry_constraints.csv << 'EOF'
# 标签, 实测距离(m), 起点x, 起点y, 终点x, 终点y
走廊长度,30.50,1.20,0.35,31.05,1.80
房间A宽度,6.00,-0.50,0.10,-0.50,6.05
柱间距,3.20,5.00,2.00,8.15,2.10
EOF
```

**步骤四**: 运行测量脚本
```bash
# 基线
python3 ~/go1_ws/src/go1_bringup/scripts/measure_geometry.py \
    ~/go1_ws/trajectories/traj_fastlio_baseline.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/results/geometry_baseline.csv

# 改进版
python3 ~/go1_ws/src/go1_bringup/scripts/measure_geometry.py \
    ~/go1_ws/trajectories/traj_fastlio_improved.txt \
    ~/go1_ws/trajectories/geometry_constraints.csv \
    -o ~/go1_ws/trajectories/results/geometry_improved.csv
```

> **建议**: 至少准备 3-5 组约束；走廊纵向距离最有价值（baseline 在此方向漂移最严重）。

### 8.4 论文图表建议

需要准备的图表：

1. **轨迹俯视对比图**（evo_traj，baseline 蓝色 vs improved 红色，标注退化段）
2. **闭环漂移柱状图**（3 次重复实验，baseline vs improved，含误差棒）

5. **建图质量对比**（slam_toolbox 地图截图，baseline 形变 vs improved 保持一致）
6. **评估指标汇总表**（3 次实验均值 +/- 标准差）

**测试用例建议**：

| 编号 | 场景 | 距离 | 描述 |
|------|------|------|------|
| T1 | 直线无障碍 | 3m | 基本功能验证 |
| T2 | 直线无障碍 | 8m | 长距离验证 |
| T3 | L 形拐弯 | 5m | 转弯能力 |
| T4 | 狭窄通道 | 3m | 门口/走廊 |
| T5 | 动态障碍 | 5m | 有人经过 |
| T6 | 返回起点 | - | 全局规划 |

每个测试用例重复 3-5 次，取统计量。

### 9.3 查看结果

`nav_metrics.py` 订阅 Nav2 的 `/navigate_to_pose/_action/status` 话题，
每个 trial 在 Nav2 action 进入终态时**立刻**写入 CSV，无需等节点退出。

```bash
# 可随时查看（trial 完成即可见）
cat ~/go1_ws/trajectories/nav_metrics.csv
```

CSV 字段说明:

| 字段 | 含义 |
|------|------|
| `trial_id` | 递增编号 |
| `timestamp` | 写入 CSV 的墙钟时间 |
| `status` | `SUCCEEDED` / `ABORTED` / `CANCELED` |
| `duration_s` | 从 Nav2 接受目标到进入终态的耗时 (秒) |
| `path_length_m` | trial 期间 `/Odometry` 累积路径长度 (米) |
| `goal_x/y/yaw` | 最近一次 `/goal_pose` 的目标坐标 |

> **说明**: `status` 为 `ABORTED` 常见原因是全局规划失败或控制器超时；
> `CANCELED` 通常是用户在 RViz 点击了 "Cancel" 或通过 `/goal_pose` 发了新目标。

### 9.4 导航评估指标汇总

| 指标 | 计算方式 |
|------|----------|
| **导航成功率** | `SUCCEEDED` 次数 / 总 trial 数 x 100% |
| **平均导航耗时** | 所有 `SUCCEEDED` 案例的 `duration_s` 均值 |
| **平均路径效率** | `path_length_m` / 起点到目标的直线距离 |
| **最大/最小耗时** | 描述系统稳定性 |

### 10.6 尾部盲区（跟随者过滤）

文件: `~/go1_ws/src/FAST_LIO/config/mid360.yaml` 的 `preprocess.tail_fov_*` 段  
**同时修改** `config/pointcloud_to_laserscan_params.yaml` 的 `angle_min/max`（保持扇区一致）。

| 场景 | `tail_fov_half_angle` | `tail_fov_blind_range` | `angle_min/max` |
|------|:---:|:---:|:---:|
| 远距离跟随 (≥3m) | 30° | 5.0 | ±2.618 (±150°) |
| **近距离跟随 (1–2m)** (当前默认) | **40°** | **2.5** | **±2.443 (±140°)** |
| 无人跟随 | `tail_fov_blind_en: false` | - | ±π (-3.14, 3.14) 保留全圈 |

> **判断依据**:
> - 跟随越近，扇区应越宽（包含摆动），距离应越短（避免误过滤远处结构）。
> - 操作者若始终保持机器人正后方 → 半角可取 25°；若会左右摆动 → 取 40°。

### 10.7 velocity_smoother

文件: `config/go1_nav_params.yaml` 的 `velocity_smoother` 段

该节点在 TEB 与 Go1 驱动间做速度平滑，抑制高频抖动。`max_velocity` / `max_accel` 必须**大于等于** TEB 的对应值，否则 Go1 实际响应会被截断。

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `smoothing_frequency` | 20.0 | 平滑输出频率 (Hz) |
| `max_velocity` | [0.3, 0.2, 0.7] | 与 TEB 保守配置一致，上调 TEB 后同步上调 |
| `max_accel` | [1.5, 1.5, 2.0] | 与 TEB 一致 |
| `odom_topic` | /Odometry | FAST-LIO 10Hz 里程计 |

### 10.8 FAST-LIO 下采样

文件: `~/go1_ws/src/FAST_LIO/config/mid360.yaml`

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `filter_size_surf` | 0.3 | 当前帧下采样；越小越准 CPU 越高 |
| `filter_size_map` | 0.4 | 地图下采样；越小地图越密 |

## 11. 已知问题与 Bug 排查

### 11.1 TF 树冲突（最常见问题）

**症状**: 终端大量警告 `Warning: TF_REPEATED_DATA` 或 `Could not find a connection between...`

**排查步骤**：
```bash
# 1. 查看完整 TF 树
ros2 run tf2_tools view_frames
# 生成 frames.pdf，检查是否有重复的父子关系

# 2. 查看特定帧的变换
ros2 run tf2_ros tf2_echo map camera_init
ros2 run tf2_ros tf2_echo camera_init body
```

**常见冲突**:
- `robot_localization` 的 `publish_tf` 必须为 `false`（已配置）
- 使用 `use_odom_fusion:=false` 可完全规避融合相关的 TF 问题

### 11.2 时间戳不同步

**症状**: `Lookup would require extrapolation into the future`

**排查**:
```bash
# 查看各传感器时间戳是否接近
ros2 topic echo /odom --field header.stamp --once
ros2 topic echo /livox/lidar --field header.stamp --once
```

**解决**: 增大 `transform_tolerance`

### 11.3 FAST-LIO2 初始化失败

**症状**: 启动后终端一直输出 "No point, skip this scan!"

**解决**:
1. 确认 MID-360S 已通电并成功连接（检查网线/IP `192.168.1.135`）
2. 确认使用了正确的启动脚本 `msg_MID360s_launch.py`（不是 `msg_MID360_launch.py`）
3. 检查 `mid360.yaml` 中 `lid_topic` 和 `imu_topic` 是否正确（默认 `/livox/lidar` 和 `/livox/imu`）
4. FAST-LIO2 启动后前 2-3 秒输出此警告是**正常现象**（IMU 初始化），
   初始化完成后会输出 `IMU Initial Done` 并开始处理点云
5. 如果持续输出（超过 5 秒），检查 `/livox/lidar` 话题是否有数据：
   ```bash
   ros2 topic hz /livox/lidar
   ```

### 11.4 rosbag 回放相关问题

**症状**: 回放时 FAST-LIO2 不输出数据

**排查**:
```bash
# 确认 bag 包含所需话题
ros2 bag info ~/go1_ws/bags/degradation_exp1

# 确认使用了 --clock 和 --topics 参数
ros2 bag play <bag> --clock --topics /livox/lidar /livox/imu /odom /imu

# 确认 FAST-LIO2 使用了 use_sim_time
ros2 param get /fastlio_mapping use_sim_time
```

**症状**: `/odometry/filtered` 无输出（fusion 模式回放）

**排查**:
```bash
# 确认 robot_localization 使用了 use_sim_time
ros2 param get /ekf_filter_node use_sim_time

# 确认 /odom 和 /imu 话题有数据
ros2 topic hz /odom
ros2 topic hz /imu
```

### 11.5 Jetson AGX Orin 性能问题

**症状**: 节点启动缓慢，处理延迟大

**优化**:
```bash
# 切换到最大性能模式
sudo nvpmodel -m 0
sudo jetson_clocks
```

| 长廊里定位漂移 | 几何退化，AMCL 无特征可匹配 | 实机启用 `odom_constraint` (`use_odom_fusion:=true`) |

## 15. 仿真测试环境 — Ignition Gazebo Fortress（全栈闭环验证）

> **目的：** 在没有 Go1 / Mid360s 的情况下，跑通 `cmd_vel → 仿真物理 → 3D 点云 → FAST-LIO → SLAM/AMCL → Nav2 → cmd_vel` 完整闭环，**用于上机前排雷**。
>
> **与 §14 fake_robot 的区别：** §14 是 2D 射线投射假激光，只能验 Nav2 + AMCL；本节用 Ignition 物理引擎 + 3D `gpu_lidar`，把 FAST-LIO、`pointcloud_to_laserscan` 都拉进闭环，更接近实机。

### 15.1 设计取舍（B-1 方案）

为节省搭建成本，本仿真**不模拟四足步态、不模拟 Livox CustomMsg 格式**：

| 取舍点 | 仿真做法 | 后果 / 何时该升级 |
|--------|----------|-------------------|
| 机器人本体 | 0.4×0.3×0.15 砖头, `VelocityControl` 直接吃 `cmd_vel` | 不验证步态稳定性、腿部里程计；要测 `use_odom_fusion` 需另起方案 |
| LiDAR 数据格式 | Ignition `gpu_lidar` 输出标准 `PointCloud2`（无 `ring`/`time`） | FAST-LIO 用 `lidar_type: 5`（`default_handler`），实机仍用 `lidar_type: 1` |
| LiDAR 几何 | 16 行 × 1024 列, ±20° 垂直 FoV, 30 m | 与 Mid360s 真实非重复扫描有差异；点云密度更均匀 |
| 步态颠簸 | 砖头不会颠 | 退化判据 (`effct_feat_num<50`) 在仿真里几乎触发不了，**不能**用仿真验证 `odom_constraint` 行为 |

**已经满足的（可以放心用仿真验证的）：**
- Nav2 全套（AMCL/A*/TEB）配置正确性
- FAST-LIO 节点能否正常订阅、TF 是否齐全、`pointcloud_to_laserscan` 高度过滤窗口
- slam_toolbox 与 FAST-LIO 共存的 TF 链路 (`map → camera_init → body`)
- `cmd_vel` 全向（`linear.y ≠ 0`）链路是否打通

### 15.8 已知坑

| 现象 | 原因 | 解决 |
|------|------|------|
| `gz sim` 启动后无窗口 | Jetson 无显示器 / 远程 SSH 无 X11 转发 | `ros2 launch go1_bringup go1_sim.launch.py gui:=false`（仍能跑物理 + 传感器） |

| Nav2 报 `map_server` failed to load | `maps/sim_lab.yaml` 不存在 | 先跑 §15.6 建图保存 |
