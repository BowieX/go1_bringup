> 每一步都有明确的"通过判据"和"不通过时的回退路径"，尽可能减少现场调试时间、避免

## 第一部分：离线回归测试（不接硬件）

此部分在任何有 ROS2 Humble 的机器上都可以跑。每个子项 < 1 分钟，全量不到 5 分钟。

### R1. colcon 增量编译

**做什么**：

```bash
cd ~/go1_ws
colcon build --packages-select go1_bringup --symlink-install
```

**通过判据**：

```
Finished <<< go1_bringup [N.NNs]
Summary: 1 package finished [N.NNs]
```

**失败时**：

- 报找不到 `teb_local_planner`、`fast_lio` 等包 → 按 [实验手册.md §2](实验手册.md) 全量编译。

---

### R2. Launch 文件语法与参数

**做什么**：

```bash
cd ~/go1_ws && source install/setup.bash

# 打印每个 launch 的参数列表（不启动任何节点）
for lf in go1_base go1_mapping go1_nav go1_replay; do
  echo "=== $lf ==="
  ros2 launch go1_bringup ${lf}.launch.py --show-args 2>&1 | head -20
done
```

**通过判据**：

- 四个 launch 都能正常打印 `Arguments:` 表格，不抛 ImportError / AttributeError。
- `go1_base` 能看到 `use_odom_fusion`、`enable_odom_constraint`、`use_sim_time`。
- `go1_mapping` / `go1_nav` 能看到并透传 `enable_odom_constraint`。
- `go1_nav` 能看到 `map`、`params_file`、`use_odom_fusion`。
- `go1_replay` 能看到 `odom_constraint`。

**失败时**：

- `ModuleNotFoundError: ament_index_python` → 没 source `install/setup.bash`。
- `No module named 'launch'` → ROS2 环境没生效，重新 `source /opt/ros/humble/setup.bash`。

### R3. Nav2 参数加载与 lifecycle 空跑

**作用**：验证 [go1_nav_params.yaml](../config/go1_nav_params.yaml) 在没有硬件的情况下能
让 Nav2 全栈转到 `active`。这一步能提前暴露所有参数类型错误（见下方"历史 BUG 回归"）。

**做什么**：

```bash
cd ~/go1_ws && source install/setup.bash

# 后台启 Nav2，使用占位地图 test_map.yaml
# 注意: test_map.{yaml,pgm} 是仓库自带的占位地图 (内容无意义), 仅用于让
#       map_server 能 active. 真正的实验地图是建图 + PCD 切片后产出的 my_lab.*.
ros2 launch nav2_bringup bringup_launch.py \
  map:=install/go1_bringup/share/go1_bringup/maps/test_map.yaml \
  params_file:=install/go1_bringup/share/go1_bringup/config/go1_nav_params.yaml \
  use_sim_time:=False autostart:=True &>/tmp/nav2_smoke.log &
NAV_PID=$!

# 等 15 秒给 lifecycle 充分激活
sleep 15

# 逐个查 lifecycle 状态
for n in amcl map_server controller_server planner_server bt_navigator \
         behavior_server waypoint_follower smoother_server velocity_smoother; do
  printf '%-22s ' "$n"
  ros2 lifecycle get "/$n" 2>&1
done

# 收尾
kill $NAV_PID 2>/dev/null; wait 2>/dev/null
```

**通过判据**：所有 9 个节点都打印 `active [3]`。

**失败时**：

- 某个节点 `unconfigured [1]` → 看 `/tmp/nav2_smoke.log`，搜 `ERROR`：
  ```bash
  grep -E "ERROR|FATAL|Aborting" /tmp/nav2_smoke.log
  ```
- **历史 BUG 回归参考**（如果看到这类报错说明修复被回退）：
  - `parameter 'FollowPath.teb_autosize' has invalid type ... {double} ... {bool}` →
    [go1_nav_params.yaml](../config/go1_nav_params.yaml) 里 `teb_autosize` 必须写 `1.0` 不能是 `true`。
  - `parameter 'FollowPath.obstacle_cost_exponent' has invalid type ... {double} ... {integer}` →
    必须写 `1.0` 不能是 `1`。

### 阶段 A：硬件基础链路（不开 EKF）

**目标**：验证驱动、LiDAR、FAST-LIO、点云→scan 转换、TF 这条最短链路。

**启动命令**（终端 1）：

```bash
ros2 launch go1_bringup go1_base.launch.py use_odom_fusion:=false
```

等待约 5 秒，直到终端滚出 `IMU Initial Done` 或 FAST-LIO 的 `num_pts_undistort` 开始有值。

#### A.1 机器狗切入可控模式

Go1 驱动启动后默认是 `STAND_UP(6)`，必须发一次空速度把它切到 `WALK_W_VEL(2)`，否则遥控器不生效：

```bash
# 终端 2
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist '{}'
```

**通过判据**：轻推遥控器，机器狗会按遥控器指令小幅移动。

#### A.2 话题健康度

```bash
# 终端 2 一条条跑
ros2 topic hz /odom              # 期望 ~50 Hz
ros2 topic hz /imu               # 期望 ~100 Hz
ros2 topic hz /livox/lidar       # 期望 10 Hz
ros2 topic hz /livox/imu         # 期望 ~200 Hz
ros2 topic hz /Odometry          # FAST-LIO 输出，期望 ~10 Hz
ros2 topic hz /cloud_registered  # 期望 ~10 Hz
ros2 topic hz /scan              # pc2scan 输出，期望 ~10 Hz
```

**通过判据**：每个话题都稳定在期望频率 ±20% 范围内，无 "no new messages" 报警。

**失败时**：

- `/livox/lidar` 无数据 → LiDAR 未通电 / 网口未连接 / IP 不对（MID-360S 默认 `192.168.1.135`，
  Jetson 要在 `192.168.1.x/24` 同网段）。
- `/Odometry` 无数据但 `/livox/lidar` 有 → 检查 FAST-LIO 终端输出，通常是 `lid_topic`
  / `imu_topic` 写错，见 [mid360.yaml](../../FAST_LIO/config/mid360.yaml)。
- `/scan` 无数据但 `/cloud_registered` 有 → pc2scan 的 TF 链断，见 A.3。

#### A.3 TF 树完整性（阶段 A 关键检查）

```bash
# 终端 2，约 3 秒后生成 frames.pdf
ros2 run tf2_tools view_frames
```

打开生成的 `frames_*.pdf`，**期望看到如下连接**：

```
camera_init  ──>  body  ──>  livox_frame
                          (static, 数值见 config/lidar_extrinsics.yaml,
                           当前实测 x=0.008, y=0, z=0.2742)

unitree_odom  ──>  unitree_base         (与上方 tree 独立, 不相交)
```

**通过判据**：

- `body` 有且仅有 1 个父节点 `camera_init`（FAST-LIO 发布）
- `unitree_base` 的父是 `unitree_odom`（unitree_ros 发布）
- 两棵子树互不相交

**失败时**：

- 如果 `body` 有两个父（既是 `camera_init` 子又是 `unitree_base` 子）→ 说明
  `go1_base.launch.py` 可能还残留旧的 `unitree_base → body` 身份 TF
  (2026-04-23 架构整改时已删除, 若仍见到请检查是否 rebuild 过). 现架构中
  `use_odom_fusion:=true` 不再造成 body 双父, 详见 [实验手册 §12](实验手册.md).
- 如果 `camera_init → body` 不存在 → FAST-LIO 没正常启动，见 A.2。

#### A.4 时间戳对齐

```bash
# 终端 2
ros2 topic echo /Odometry --field header.stamp --once
ros2 topic echo /scan     --field header.stamp --once
ros2 topic echo /odom     --field header.stamp --once
```

**通过判据**：三条时间戳秒数相差 < 1s（Jetson 与 Go1 未强制对时，允许秒级偏差）。

**失败时**：如果相差 > 10s，检查 Jetson 系统时间。建图和 AMCL 对时间戳宽容度有限，
偏差太大会看到 "Lookup would require extrapolation into the future" 警告。

**阶段 A 退场**：终端 1 按 `Ctrl+C`，**在 3 秒内**完成。如果超时让狗站着不动可以，
但不要用 `kill -9`，否则狗可能保持最后一条速度继续跑（见 [紧急停止规程](#紧急停止规程必读)）。

### 阶段 B：SLAM 建图验证（FAST-LIO 在线 + PCD 离线切片）

**目标**：生成 Nav2 可直接加载的 2D 栅格地图（`my_lab.pgm + my_lab.yaml`）。

**路线说明**（为什么不是 slam_toolbox）：Go1 高频 Z/Pitch 抖动让 2D 扫描匹配在
长廊等退化场景旋转约束极弱、走 8 字会出现角度偏差；而 FAST-LIO 3D 融合了 IMU，
点云质量明显更好。所以现在只用 FAST-LIO 在线累积 3D PCD，**退出后离线切片**生成
2D 地图。Nav2 全栈一字不改。

**启动命令**：

```bash
# 终端 1
ros2 launch go1_bringup go1_mapping.launch.py use_odom_fusion:=false
```

RViz 会自动打开 [go1_mapping.rviz](../config/go1_mapping.rviz) 配置（Fixed Frame 为
`camera_init`，已移除 Map display）。

**预检查**（对 PCD 累积至关重要）：
1. [mid360.yaml](../../FAST_LIO/config/mid360.yaml) 中 `pcd_save.pcd_save_en: true` 且 `interval: -1`。
2. [laserMapping.cpp:650-677](../../FAST_LIO/src/laserMapping.cpp#L650-L677) 的 per-frame
   PCD 累积块**未被注释**。曾因此块被 `/* */` 注释导致 `scans.pcd` 为 0 字节。

#### B.1 在线建图观察

在 RViz 中重点看：
- `RegisteredCloud`（话题 `/cloud_registered`）：全局 3D 点云，随运动增长
- `Odometry`（话题 `/Odometry`）：FAST-LIO 位姿轨迹
- `LaserScan`（话题 `/scan`）：仅用来确认后方盲区过滤（±40° 扇区）工作正常

遥控机器狗缓慢走一圈（< 0.3 m/s），覆盖整个实验区域。**推荐走 8 字路径**经过同一
位置两次，验证无重影（这是 slam_toolbox 之前最常翻车的地方）。

**通过判据**：
- `/cloud_registered` 点云持续扩大，墙体/柜子等结构叠合清晰（无重影）
- `/Odometry` 轨迹连续无跳变
- 8 字路径二次经过时，RViz 中看到的墙面叠合良好

**失败时**：
- 点云明显漂移 / 长廊弯曲 → LiDAR 外参错误，按 [实验手册 §4.5](实验手册.md) 重测。
  或场景本身几何退化过于严重 → 考虑后续 D 阶段启用 EKF 里程计约束。

#### B.2 安全退出并触发 PCD 保存

在终端 1 按 `Ctrl+C`（**不要** `kill -9`）。FAST-LIO 的 SIGINT handler 会把
`pcl_wait_save` 写到 `~/go1_ws/src/FAST_LIO/PCD/scans.pcd`。**等 launch 完全退出**
（shell 提示符回来）后再继续。

```bash
# 终端 2
ls -la ~/go1_ws/src/FAST_LIO/PCD/scans.pcd
# 期望: 几百 MB 级别 (10 分钟建图约 500 MB - 1 GB)
```

**失败时**：
- 文件不存在 / 为 0 字节 → 检查 B 阶段"预检查"两项；若都正确，看
  [实验手册 §11](实验手册.md) 的 PCD 相关排查。
- `Ctrl+C` 被 bash 包装脚本截获而没传给 `ros2 launch` 进程 →
  ```bash
  pgrep -f "bin/ros2 launch"   # 找到真正的 PID
  kill -INT <PID>
  ```

#### B.3 离线切片生成 2D 地图

```bash
# 终端 2
ros2 run go1_bringup pcd_to_map \
    ~/go1_ws/src/FAST_LIO/PCD/scans.pcd \
    ~/go1_ws/src/go1_bringup/maps \
    my_lab \
    --z-min 0.05 --z-max 0.25 \
    --resolution 0.05 \
    --hit-threshold 2 \
    --padding 0.5
```

**通过判据**：
- 脚本 4 步全部输出 `[OK]`，生成 `my_lab.pgm + my_lab.yaml`
- 典型规模：`672x1013` 栅格、占据 1w-5w 格、空闲 50w-100w 格
- `my_lab.yaml` 的 `resolution: 0.05`、`origin: [x, y, 0.0]` 数值合理

**检查地图质量**：
```bash
xdg-open ~/go1_ws/src/go1_bringup/maps/my_lab.pgm &
```
墙体应是连续黑线、走廊连续空闲、8 字路径两次经过**无重影**。

**失败时**：
- 墙太稀疏 / 断裂 → 降低 `--hit-threshold`（例如 1）
- 噪点过多 / 地面被当墙 → 抬高 `--z-min` 到 0.08；或提高 `--hit-threshold`
- 切片点为 0 / 尺寸异常 → 检查 FAST-LIO 地图是否以地面 Z≈0 为基准
  （默认 `camera_init` 原点 = 启动时机器人 IMU 处，Z 向上），调整 `--z-min/--z-max`

#### B.4 重编译把地图装进 install

**重要**：保存后必须重新 build，`go1_nav.launch.py` 读取的是 install 路径：

```bash
cd ~/go1_ws
colcon build --packages-select go1_bringup --symlink-install
source install/setup.bash
```

**阶段 B 退场**：若在线阶段仍开着，先 `Ctrl+C` 终端 1。

### 阶段 C：Nav2 导航全栈验证

**目标**：用刚建的地图跑一次 Nav2，验证能规划路径并驱动机器狗到达目标点。

**启动命令**：

```bash
# 终端 1
ros2 launch go1_bringup go1_nav.launch.py use_odom_fusion:=false
```

等待 ~15 秒（Nav2 生命周期激活需要时间）。

#### C.1 生命周期状态

```bash
# 终端 2
for n in amcl map_server controller_server planner_server bt_navigator \
         behavior_server waypoint_follower smoother_server velocity_smoother; do
  printf '%-22s ' "$n"; ros2 lifecycle get "/$n" 2>&1
done
```

**通过判据**：9 个节点全部 `active [3]`。

**失败时**：

- 任何节点 `unconfigured` / `inactive` → 看终端 1 的日志 grep `ERROR|FATAL`。常见：
  - map_server 报 `Map file not found` → `my_lab.yaml` 还没 build 进 install。回到 B.2 最后一步。
  - controller_server 报参数类型错误 → 参考 [R3](#r3-nav2-参数加载与-lifecycle-空跑) 的历史 BUG 条目。

#### C.2 AMCL 初始定位

在 RViz 中：

1. 顶部工具栏选 **"2D Pose Estimate"**，在地图上点击机器狗的真实位置并拖动箭头对准朝向。
2. 观察 `/amcl_pose` 话题：

```bash
# 终端 2
ros2 topic echo /amcl_pose --once
```

**通过判据**：`covariance` 对角线值随机器狗移动逐步减小（粒子收敛）。

#### C.3 手动发送导航目标

在 RViz 中选 **"Nav2 Goal"**，点击地图空旷处。

**通过判据**：

- 全局路径（绿色）从机器狗指向目标点。
- 局部路径（红色 / 蓝色，TEB 输出）跟随全局路径。
- 机器狗实际移动（轻推遥控器前先确认开关在 `WALK_W_VEL`，见 A.1）。
- `/cmd_vel_nav`（smoother 前）和 `/cmd_vel`（给驱动）都有流量：
  ```bash
  ros2 topic hz /cmd_vel_nav
  ros2 topic hz /cmd_vel
  ```

**失败时**：

- 有全局路径但机器狗不动 → 检查 `/cmd_vel` 是否在发布；检查 C.1 中的
  `velocity_smoother` 是否 active。
- 机器狗乱转不朝目标走 → AMCL 定位漂移，在 RViz 重新 **2D Pose Estimate**。
- TEB 报 "Infeasible trajectory" → 把 [go1_nav_params.yaml](../config/go1_nav_params.yaml)
  的 `max_vel_x` 临时降到 `0.2`、`acc_lim_x` 降到 `0.5` 再试。

**阶段 C 退场**：先发一个 `/cmd_vel` 零速度（见 [紧急停止](#紧急停止规程必读)），再 `Ctrl+C`。

### 阶段 D：启用 EKF 融合（风险项集中）

> 这一阶段是本项目**风险最高的部分**。阶段 A/B/C 跑通后再来，不要跳过前面。

**已知风险**（详见本文末尾"已知风险速查表"）：

- **~~D-risk-1~~** (已根治, 2026-04-23): `body` 双父 TF 冲突. 原方案用
  `unitree_base → body` 身份 TF 桥接两棵子树, 导致 FAST-LIO 的 `camera_init → body`
  与桥接 TF 冲突. 现已改为**两棵子树互不相交** (见 §12): EKF `base_link_frame` 改为
  `unitree_base`, 另加 `unitree_base → imu` 身份 TF 让 EKF 能变换 /imu. 若
  `frames.pdf` 仍看到 `body` 双父, 说明 `unitree_base_to_body_tf` 残留, 清理重跑.
- **~~D-risk-2~~** (已根治): EKF 的 `world_frame/odom_frame` 已改为
  `unitree_odom`, 与 `/odom` 的 `header.frame_id` 对齐；不再引入额外的里程计根坐标系。

#### D.1 启动

```bash
# 终端 1
ros2 launch go1_bringup go1_base.launch.py use_odom_fusion:=true
```

#### D.2 验证 TF 森林不冲突（关键）

**启动后 5 秒内**执行：

```bash
# 终端 2
ros2 run tf2_tools view_frames
```

打开生成的 `frames_*.pdf`。

#### D.3 验证 /odometry/filtered 真的受 /odom 影响

理论上 EKF 会把 `/odom`（腿部里程计）与 `/imu`（机体 IMU）融合输出 `/odometry/filtered`。
当前配置的输出帧是 `unitree_odom → unitree_base`，与原始 `/odom` 对齐，避免跨根 TF 查询。

**测试步骤**：

```bash
# 终端 2
# 1. 先看 EKF 输出是否有数据
ros2 topic hz /odometry/filtered          # 期望 ~50 Hz

# 2. 记录静止时 EKF 输出的前 5 秒（机器狗完全不动）
timeout 5 ros2 topic echo /odometry/filtered --field pose.pose.position > /tmp/ekf_still.txt
wc -l /tmp/ekf_still.txt

# 3. 用遥控器让机器狗前进 1m 左右
# 4. 再次记录
timeout 5 ros2 topic echo /odometry/filtered --field pose.pose.position > /tmp/ekf_moving.txt

# 5. 对比静止与运动时 x/y 的数值范围
head -20 /tmp/ekf_still.txt
head -20 /tmp/ekf_moving.txt
```

**通过判据**：运动时 `x`/`y` 数值明显变化（> 0.5m 范围内），静止时几乎不变。

**失败时**（`/odometry/filtered` 在运动时几乎不动）：

- 打开调试日志看 EKF 是不是在丢数据：
  ```bash

  # 然后重启 EKF 单独看 log:
  ros2 run robot_localization ekf_node \
    --ros-args --params-file install/go1_bringup/share/go1_bringup/config/ekf_odom_fusion.yaml \
    --log-level debug 2>&1 | grep -iE "transform|dropped|reject"
  ```
- 如果仍看到类似 "Could not obtain transform from unitree_odom to ..." 的日志，优先确认
  [ekf_odom_fusion.yaml](../config/ekf_odom_fusion.yaml) 已安装为新版：
  `odom_frame/world_frame` 都应为 `unitree_odom`。修改源码配置后要重新 build/source。

## 紧急停止规程（必读）

**背景**：[unitree_ros 驱动](../../unitree_ros/src/unitree_driver.cpp) 只有在析构函数里才调用
`stop()`。如果用 `kill -9` 强杀，或者 launch 进程因异常崩溃，机器狗会**保持最后一条
cmd_vel 速度继续运动**，可能撞墙或撞人。

**规则**：

1. **永远不要用 `kill -9 <unitree_driver pid>`**。
2. 任何关闭流程**先发零速度**，再 `Ctrl+C`：

   ```bash
   ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
     '{linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}'
   ```

3. 把上面这条命令**粘贴到一个备用终端随时待命**，实机联调期间不要关这个终端。
4. 遥控器在手边、电池插拔工具在手边（最终保险）。

## 附录：一条命令扫描所有 launch 错误
